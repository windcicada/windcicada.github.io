## Page 1: Package environment configuration and coast-assistant

The package version is suitable for users who "get a pre-packaged running package and then run the calculation example on the Linux server". Common directory names are similar to:
```text
coast-runtime-<version>-linux-x86_64/
```
Packaged versions usually come with solvers, `coastctl`, `coast_remap`, template studies, documentation, WebUI and nanobot runtime assets. In the new environment, first confirm that the server is Linux x86_64 and that `python3` and `mpirun` can be found:
```bash
which python3
which mpirun
```
After decompression, enter the package root directory. If you choose to run it in place, you can directly use the tools in the package:
```bash
cd coast-runtime-<version>-linux-x86_64
bin/coast-assistant --self-test --require-runtime --json
bin/coast-assistant --configure-model
bin/coast-assistant
```
If you choose to install to a fixed location, you can run:
```bash
./install.sh /opt/coast/runtime
source /opt/coast/runtime/env/coast-env.sh
coast-assistant
```
`bin/coast-assistant` is the novice entrance to the packaged version. It is not the solver itself, but an assistant launcher: it will call the COAST MCP tool in the package to help you check the calculation example, read and modify the input file, view the mesh and boundary, do pre-run checks, start controlled short runs, monitor `screen` and run logs. When you need a browser interface, you can ask the assistant to open the WebUI; the left side of the WebUI is chat, and the right side is the file and run workbench.

In the packaged version, if you start the real solver through assistant/nanobot, you still have to follow the safety process: preflight first, then confirm startup, and then monitor the process, `screen` and monitor. Do not let the assistant use ordinary shell commands to bypass the controlled process to start the solver; if you do not use the assistant, please follow the ordinary manual commands in the running chapter of this manual. If you encounter other problems, such as "how to change the inlet temperature", "why preflight does not pass", "what does this error in the screen mean", "how to download the Visit results", you can directly ask `coast-assistant` and let it check with the tools in the project before giving suggestions.

# 0. Introduction to the manual

Welcome to COAST. This manual is written for users who are new to COAST. By default, readers do not need to have a programming foundation, nor do they need to learn computational fluids, combustion, parallel computing or Linux system management. All you need to know is that you need to log into the Linux server via SSH, prepare a calculation, check the settings, run the calculation from the command line, and view the results.

This part is responsible for the first introductory content, mainly talking about the package version, that is, how to use the portable running package. If you get a packaged `coast-runtime-<version>-linux-x86_64` directory, you can start here.

## 0.1 Who is this manual for?

This manual is suitable for the following users:

- I want to run COAST first and understand the process from preparation, running to viewing results;
- You need to operate COAST on the Linux server through the SSH command line on a Windows computer;
- Don’t want to touch the source code, compilation, test scripts and development directories from the beginning;
- Want to know what the words `EXEC_TEMPLATE`, `*.d`, `Restart`, `Visit`, and port forwarding mean;

## 0.2 Which path is recommended for novices to take first?

Newbies are recommended to use the encapsulated version of the SSH command line path:

1. Use SSH to log in to the Linux server on the Windows side.
2. Unzip the COAST portable package on the Linux server.
3. Copy `EXEC_TEMPLATE` to create your own working study.
4. Use a text editor or command line tool to modify the `*.d` settings file.
5. Use the command line to inspect the study, boundaries, and mesh.
6. Use `coastctl run --preflight` to do a pre-start check, and then use `coastctl run --execute` to start the calculation.
7. Use `coastctl monitor`, `screen`, external `.coast_run_logs/` log and `Visit/` to view the running status and results.
8. If you really need graphical preview, start the graphical auxiliary interface separately; it is not the main line running mode.

The advantage of this path is that you don't need to compile the program or install a complete development environment on your local machine. The portable package already contains the `coast-solver` executable program, command line helpers, clean study templates and necessary documentation required to run it.

The carrying case also offers the nanobot assistant as an optional newbie assistant. Run in browser mode
`bin/coast-nanobot-webui --package-root .`, the left side is the dialogue and the right side is COAST
Workbench for uploading, file viewing/editing/downloading, pre-run checks, sprinting, monitoring, stopping and logging
tail; run `bin/coast-nanobot-chat --package-root .` in terminal mode. assistant should only pass
COAST MCP tool operation must pass preflight before actual operation, and requires explicit confirmation.

## 0.3 What is the difference between the encapsulated version and the unencapsulated version?

COAST has two common forms: encapsulated version and unencapsulated version. They are two program forms for different purposes: the packaged version is used for daily running calculation examples, and the unpackaged version is used for source code development, compilation, testing and maintenance.

### 0.3.1 What is the packaged version?

The packaged version is also called a portable runtime package, which is usually a directory like this:
```text
coast-runtime-<version>-linux-x86_64/
  SKILL.md
  bin/coast-solver
  bin/coast_remap
  bin/coastctl
  bin/coast-ui
  bin/coast-mcp
  bin/coast-standard-test
  bin/coast-nanobot-chat
  bin/coast-nanobot-webui
  env/coast-env.sh
  EXEC_TEMPLATE/
  ui/static/
  docs/USER_MANUAL.md
  docs/COAST_NANOBOT_ASSISTANT.md
  nanobot/
  agent_skills/
  manifest.json
  PACKAGE_AUDIT.json
  install.sh
```
The packaged version can be understood as a "organized running toolbox". It contains:

- `bin/coast-solver`: COAST’s solver ontology, the program that actually performs calculations;
- `bin/coast_remap`: C++ Restart remapping backend, `coastctl run` is used by default when the old Restart needs to be prepared to the new runtime mesh;
- `bin/coastctl`: command line operation tool, used to check calculation examples, view grid status, start running, monitor and stop;
- `bin/coast-ui`: Optional graphical auxiliary interface backend, generally not used as the mainline running mode;
- `bin/coast-nanobot-webui` and `bin/coast-nanobot-chat`: optional nanobot
  assistant entrance, respectively used for browser left chat/right workbench and terminal dialogue;
- `bin/coast-mcp` and `bin/coast-standard-test`: used by assistant and standard checks
  controlled tool access;
- `env/coast-env.sh`: environment setting script, used to tell the current terminal where to find the COAST tool;
- `EXEC_TEMPLATE/`: clean calculation example template, which should be copied before use;
- `docs/`: documentation;
- `agent_skills/`: Operation instructions for automated assistants.

Packaged versions usually do not contain complete source code, development and test directories, large `Restart` data or large `Visit` results. Ordinary users do not need these contents when running calculation examples daily.

### 0.3.2 What is the unpackaged version?

The unpackaged version is a complete development workspace, usually similar to:
```text
Coast_software/
  SKILL.md
  docs/
  scripts/
  tests/
  SRC.Coast/
  EXEC/
```
The unpackaged version includes source code, tests, tool scripts and default development examples. It is suitable for developers, maintainers or users who need to recompile COAST. For example:

- Modify the COAST program source code;
- Rebuild the development moderator executable program;
- Run development tests;
- Package new packaged version;
- Debug grid, restart, parallel exchange and other low-level methods.

Note: If you just want to run existing calculation examples, modify input files, and view results, it is not recommended to start directly from the unpackaged version at the novice stage. The unpackaged version can do more and is more likely to accidentally delete or modify key files.

### 0.3.3 How to choose between the two

If you get the package package and the goal is to "run the calculation example", please use the package version.

If you need to modify the program source code, recompile COAST, or someone explicitly asks you to work in `SRC.Coast`, `tests`, `scripts`, then use the unpackaged version.

A simple way to judge:

| What do you want to do | Recommended use |
| --- | --- |
| Trial COAST for the first time | Packaged version |
| Create your own working study | Packaged version |
| Edit study settings using browser | Packaged version |
| Check bounds and mesh | Packaged version |
| Start calculation with a limited number of steps | Packaged version |
| View Visit output | Packaged version |
| Modify COAST source code | Unpackaged version |
| Recompile the program | Unpackaged version |
| Package new runtime package | Unpackaged version |

## 0.4 Safety principles to remember when reading this manual

First, don't modify `EXEC_TEMPLATE` directly. It is a clean template and should be left as is. Every time you do a demonstration, test or formal calculation, first copy a working example, such as `EXEC.demo`, `EXEC.my_case`.

Second, do not delete these directories in user calculations:
```text
Restart/
runtime_mesh/
Decomp/
Geometry/
Visit/
```
These directories may hold restart data, running grids, parallel partitions, geometry files, and results files. After deletion, some calculations may not be continued and some results may not be opened again.

Third, don’t start long-term formal calculations right away. It is recommended to do a short step test first to confirm that the calculation example can be started normally, that there are no obvious errors in the boundaries, and that the output directory is normal before doing the formal calculation.

Fourth, when a Windows browser accesses the COAST graphical interface on a Linux server, SSH port forwarding is usually required. The browser address looks like `127.0.0.1`, but the real program is running on a Linux server.

## 0.5 Quick check on common terms

### COAST

COAST is the name of the calculation program. It is responsible for reading the study setup, mesh, boundary conditions and initial data, and then performing numerical calculations of flow, combustion or related physical processes.

In the encapsulated version, the program that actually performs the calculation is usually:
```text
bin/coast-solver
```
### Calculation example

A calculation example is a "folder of a calculation task". It contains the input files, grid information, boundary conditions, restart data and output results required for this calculation.

`EXEC_TEMPLATE` in the package version is a template calculation example. You should copy it to get your own working example, for example:
```text
EXEC.demo/
EXEC.engine_test/
EXEC.case001/
```
### Grid

A grid is a way of dividing the computational space into many small grids. COAST does not directly calculate in continuous space, but gradually calculates velocity, pressure, temperature, components and other quantities on these small grids.

The grid can be understood as "graph paper for calculations". The finer the grid, the better it can describe complex structures, but the amount of calculation is also greater.

### Boundary

Boundaries are the outer shell or internal solid surfaces of the calculation area. Common boundaries include entrances, exits, and walls.

- Inlet: the fluid enters the calculation area from here;
- Exit: where the fluid leaves the calculation area;
- Wall: a solid surface that fluid cannot pass through;
- IBM Surfaces: Complex geometric surfaces identified by the immersed boundary method.

Boundary conditions tell COAST: "What physical state should be on this boundary." For example, what is the inlet velocity, what is the temperature, how to handle the outlet pressure, and whether there is no slip on the wall.

### Restart

`Restart` is the restart data directory. It saves the calculation state at a certain moment so that COAST can continue calculation from this state instead of starting from scratch every time.

You can think of `Restart` as a game save. If there is no archive, you can only start from the initial state; if there is an archive, you can continue from the middle.

Note: `Restart` files are usually related to the number of ranks for parallel calculations. The direct command for ordinary users is still `cd EXEC && mpirun -np N ./coast`. If MPI size differs from the active runtime mesh rank count, and `input.d` and Mesh-5 configuration allow startup regrid / restart remap, the startup phase will take the controlled preflight/write/remap path before solver reads fields and write brief diagnostics to `screen`. If the rank, Restart file, mesh identity, remap backend, or gate conditions are not met, startup will fail and close with diagnostics retained, rather than semi-automatically entering solution.

### Visit

`Visit` is the results output directory, also often refers to a set of result files used by VisIt visualization software. COAST typically generates:
```text
Visit/solution.visit
Visit/solution.<step>.domain.<rank>.vtk
```
Among them, `solution.visit` is like a directory list, which references many `.vtk` chunked result files. Simply copying `solution.visit` is usually not enough, the `.vtk` file it references must be brought along.

Note: The `Visit` directory here is related to the name of the VisIt software. The term `Visit` is retained in the manual.

### Server

A server usually refers to a Linux machine running COAST. It might be a remote high-performance computing node, a workstation, or a Linux host in the lab.

COAST calculations are typically run on Linux servers because they are computationally intensive, dependent on the Linux environment, and may require multiple CPU cores or MPI parallelism.

### Graphical auxiliary interface

The graphical auxiliary interface is a browser interface. The packaged version of COAST provides a Chinese graphical auxiliary interface, which allows you to check the status of calculation examples, modify commonly used `*.d` files, preview boundaries and grids, monitor operations, and organize Visit output without having to memorize many commands directly.

The GUI backend is launched on a Linux server and Windows users access it via a browser.

### Port

The port is the house number of the network service. COAST GUI The default example uses the `18765` port.

If the graphical auxiliary interface is started at `127.0.0.1:18765` of the server, it means: there is a web service on the 18765 port of the server that only allows local access.

### Port forwarding

Port forwarding is a "secure channel" provided by SSH. It can connect a local port on a Windows computer to a port on a Linux server.

For example:
```powershell
ssh -N -L 18765:127.0.0.1:18765 user@server
```
This means: When `127.0.0.1:18765` is opened on the Windows machine, SSH will forward the access to `127.0.0.1:18765` on the server.

This is why the browser enters the local address, but what is seen is the COAST graphical interface page on the server.

# 1. First time meeting COAST

This chapter explains the basic workings of COAST in a way that does not rely on professional background. You don’t need to memorize all the terms right away, just know what each thing is responsible for.

## 1.1 What COAST does in a calculation

A COAST calculation can be roughly thought of as the following process:
```text
Read case files
  -> Read or generate the mesh
  -> Identify boundaries and geometry
  -> Read the initial state or Restart
  -> Advance the calculation by time step
  -> Periodically write Restart and Visit results
```
That said, COAST requires several key inputs:

- Calculation example settings: how long should be calculated this time, what is the output frequency, and which physical models should be used;
- Grid: How the calculation area is cut into small grids;
- Boundary conditions: How to deal with entrance, exit and wall respectively;
- Initial state: starting from scratch or continuing from a `Restart` archive;
- Running resources: How many ranks to use for parallel computing.

During the calculation, COAST will write the result:

- `screen` or related logs: text information during runtime;
- `Restart/`: archive that can continue calculation;
- `Visit/`: Visualized results;
- Other diagnostic files: e.g. probe, heat release or statistical output.

## 1.2 What is a calculation example?

A study is a complete working folder. You can think of it as a project folder that contains everything needed for this calculation.

There is a template in the package version:
```text
EXEC_TEMPLATE/
```
You should not run formal calculations directly on the template, but make a copy:
```text
EXEC.demo/
```
The copied `EXEC.demo` is your working example. Your subsequent editing of `input.d`, `boundary_conditions.d`, starting calculations, and generating results all occur in this working example.

A typical working example might look like this:
```text
EXEC.demo/
  input.d
  ibm_mesh.d
  boundary_conditions.d
  vtk_output.d
  spray.d
  spark.d
  probe.d
  heat_release.d
  Geometry/
  Decomp/
  Restart/
  runtime_mesh/
  Visit/
  screen
```
Not every study example starts with all directories. Some directories appear after generating a mesh, starting a calculation, or writing out results.

## 1.3 What are `*.d` files?

Many of COAST's input settings are placed in text files ending with `.d`, for example:

| Documentation | Main Purpose |
| --- | --- |
| `input.d` | Controls restart, total steps, output intervals, combustion and common solver settings |
| `ibm_mesh.d` | Controls geometry, mesh, IBM scan and static mesh related settings |
| `boundary_conditions.d` | Set up inlets, outlets, walls, coordinate selectors and components |
| `vtk_output.d` | Set which result fields Visit/VTK outputs |
| `spray.d` | Spray and evaporation related settings |
| `spark.d` | Ignition source related settings |
| `probe.d` | Pressure probe related settings |
| `heat_release.d` | Heat release diagnosis related settings |

These files are normal text files and can be opened with an editor. The packaged version of the graphical auxiliary interface will make some of the commonly used settings into forms, reducing the chance of manual editing errors.

Note: Being able to open it does not mean that you can change it at will. At the novice stage, it is recommended to first modify common items through the graphical auxiliary interface, or strictly follow the instructions in subsequent chapters.

## 1.4 Why is the grid important?

COAST calculates the change of fluid in space and time. Computers cannot directly process infinite continuous space, so the area must first be cut into many small units, and these small units are grids.

Grids affect:

- Calculate whether geometric shapes can be recognized;
- Are the entrances, exits and walls located correctly?
- Whether the results are detailed enough;
- Computing speed and memory usage;
- Whether `Restart` can continue to be used.

If the mesh is too coarse, small structures may not be visible. If the grid is too fine, calculations can be very slow. For novices, there is no need to design complex grids by themselves when getting started for the first time. It is more important to learn to view the grid status and preview the boundaries first.

## 1.5 Why are boundaries important?

Boundary conditions tell COAST how the calculation area is connected to the outside world. Even if the mesh is correct and the boundary conditions are written incorrectly, the calculation may fail or result in physically meaningless results.

Common examples:

- The direction of the inlet velocity is reversed, and the fluid may flow in from the outlet direction;
- The outlet is not set correctly and the pressure wave may be reflected;
- Wall leakage, fluid may pass through areas that should be solid;
- If the component name is written incorrectly, the corresponding species may not be found in the combustion calculation.

The packaged version supports setting boundaries through `boundary_conditions.d`. It also supports coordinate selection boundaries, that is, using spatial ranges to specify which outer boundary grids belong to entrances, exits, or walls. This way common boundaries can be set even without the patch STL tag.

## 1.6 Why Restart is like "Archive"

Long calculations are not suitable for starting from scratch every time. COAST will write the status at certain times to the `Restart/` directory, and you can continue from there next time.

`Restart` usually includes data corresponding to each parallel rank. Rank can first be understood as "the number of jobs divided during parallel computing". If an example is run with 128 ranks, COAST may divide the data into 128 parts.

This is why special attention should be paid to the rank number when continuing the calculation. When the number of ranks, grids, and restart files do not match, COAST may fail to start.

Note: Do not delete `Restart/` just because it is large. Before deleting, you must confirm that renewal is no longer needed or that a backup has been saved.

## 1.7 Why can’t Visit result send only one file?

COAST's Visit output is generally not a single result file, but a set of files.

Common structures are:
```text
Visit/
  solution.visit
  solution.000010.domain.000000.vtk
  solution.000010.domain.000001.vtk
  solution.000010.domain.000002.vtk
  ...
```
`solution.visit` is like a directory listing, telling the VisIt software which `.vtk` files correspond to each time step. The real bulk of the data is in the `.vtk` files.

So when sharing results, you can’t just send:
```text
Visit/solution.visit
```
The `.vtk` file it references also needs to be sent along. Otherwise, others may only see empty results or report errors when they open it.

## 1.8 Why Linux server and Windows side connections are usually needed

Many users' daily computers are Windows, and the COAST operating environment is usually on a Linux server. This is because:

- COAST has a large amount of calculation and is suitable for running on a server or workstation;
- Parallel computing, MPI, running scripts and file permissions are more common on Linux;
- Servers may have more CPU cores, more memory, and a more stable long-running environment.

But users don't have to sit in front of the server. Common working methods are:
```text
Windows computer
  Open the graphical assistant interface in a browser
  Set up SSH port forwarding in PowerShell
        |
        |  Secure connection
        v
Linux server
  Unpack the COAST portable package
  Store case files
  Start coast-ui
  Run the COAST calculation
```
The effect of this is: the calculation remains on the server, and the operation interface is displayed in the Windows browser.

Among them:

# 2. Get started quickly with the packaged version

This chapter walks through the first-time use process of the packaged version from the perspective of a new user. The command explains where to execute it and what you should see after execution.

For convenience of explanation, the following assumptions are made:

- The Linux server username is `user`;
- The Linux server address is `server`;
- The COAST portable package file name is similar to `coast-runtime-2026.06-linux-x86_64.tar.gz`;
- The unzipped directory is called `coast-runtime-2026.06-linux-x86_64`;
- The working example is called `EXEC.demo`;
- Graphical auxiliary interface uses port `18765`.

In actual use, please replace `user`, `server`, version number and path with your real information.

## 2.1 Prepare Linux server terminal

First log in to the Linux server. You can use Windows PowerShell:
```powershell
ssh user@server
```
This command is executed in Windows PowerShell. `user` is the server username, `server` is the server address, which can be a hostname or IP address.

After execution, if this is the first time connecting, PowerShell may ask whether to trust the server fingerprint. After confirming that the address is correct, enter `yes`. Then enter the server password or use the key to log in.

After successful login, you will see the Linux command prompt. Subsequent decompression and graphical auxiliary interface commands will be executed in this Linux terminal.

## 2.2 Upload or find the COAST carrying bag

If the administrator has placed the portable package on the server, you only need to change into the directory where it is located.

If the portable package is on a Windows machine, you can use `scp` to upload it. This command is executed in Windows PowerShell:
```powershell
scp .\coast-runtime-2026.06-linux-x86_64.tar.gz user@server:~
```
The meaning is: Upload the compressed package in the current Windows directory to the server user's home directory.

After successful execution, there will generally not be a long output. You can check if the file exists after logging into the server:
```bash
ls -lh ~/coast-runtime-2026.06-linux-x86_64.tar.gz
```
This command is executed in the Linux server terminal. Normally, you will see the file size and file name.

## 2.3 Unzip the portable bag

In the Linux server terminal, enter the directory where you want to put COAST, such as your home directory:
```bash
cd ~
```
Unzip the compressed package:
```bash
tar -xzf coast-runtime-2026.06-linux-x86_64.tar.gz
```
After execution, a directory will be generated:
```text
coast-runtime-2026.06-linux-x86_64/
```
Enter this directory:
```bash
cd coast-runtime-2026.06-linux-x86_64
```
Check if there are key files inside:
```bash
ls
```
Under normal circumstances, you should see something like:
```text
SKILL.md  bin  docs  env  EXEC_TEMPLATE  install.sh  manifest.json
```
If you don't see `bin`, `env`, `EXEC_TEMPLATE`, it means you may not have entered the correct directory, or the compressed package is incomplete.

## 2.4 Choose to install or run in place

There are two ways to use the packaged version: install it in a fixed directory, or run it in place in the unzipped directory.

### 2.4.1 Run in place

If you are a novice trying it out for the first time, it is recommended to run it in place first. This will not copy the file elsewhere, and the path relationship is the most intuitive.

Execute in the package root directory:
```bash
source env/coast-env.sh
```
This command will set the current terminal environment. There is usually no output if the execution is successful.

Then check if `coastctl` is available:

## 2.7 Optional Assist: Setting up SSH port forwarding on Windows

If the COAST GUI is launched on a remote Linux server, Windows browsers generally cannot directly access the server's `127.0.0.1:18765`. Because the server's `127.0.0.1` refers to the server itself, not your Windows computer.

At this time, you need to open a new window in Windows PowerShell and execute:
```powershell

```
Please replace `user@server` with your server username and address.

The meanings of several parts of this command are as follows:

- `ssh`: connect to the server;
- `-N`: Only establish a connection and do not open the remote command line;
- `-L 18765:127.0.0.1:18765`: Forward the 18765 port of the Windows machine to the 18765 port of the server machine;
- `user@server`: your server login information.

After a successful execution, the PowerShell window usually stays there with no apparent output. This is normal. As long as this window remains open, port forwarding remains in effect.

Note: Do not close this PowerShell window. After closing, the channel from the browser to the server graphical auxiliary interface will also be disconnected.

## 2.10 Optional auxiliary: What can the graphical interface page do?

Page names may vary slightly between versions of the COAST graphical assistance interface, but are generally organized around the following purposes.

### 2.10.1 Calculation status

The study status page is used to check which workspace and study directory are currently connected, and whether the input file is complete.

You can confirm it here:

- Is the current calculation example `EXEC.demo`, not `EXEC_TEMPLATE`;
- Whether the key `*.d` files exist;
- `Restart`, `Visit`, whether the grid directory exists;
- Check whether there are any error messages in the latest check.

If the page shows that the current calculation example is `EXEC_TEMPLATE`, you should stop the operation, return to the Linux terminal, copy a working calculation example, and then start the graphical interface.

### 2.10.2 Input file form

The input file form page is used to view and modify settings in common `*.d` files.

Common uses include:

- Adjust the number of steps, output frequency, and restart switch in `input.d`;
- View mesh and geometry settings in `ibm_mesh.d`;
- Modify the output fields in `vtk_output.d`;
- Check the relevant settings of `spray.d`, `spark.d`, `probe.d`, `heat_release.d`.

Newbies are advised to only change a small number of parameters at a time and verify them immediately after saving. Do not modify many files at once, otherwise it will be difficult to determine where an error occurred.

### 2.10.3 Boundary conditions

The Boundary Conditions page is used to view and edit `boundary_conditions.d`.

You can confirm it here:

- Which areas are entrances;
- Which areas are exits;
- Which areas are walls;
- Boundary selection whether to use coordinate ranges or IBM surfaces;
- Whether the inlet velocity, temperature, pressure, and components are as expected.

If the page provides a border preview function, it is recommended to preview it after each modification. Boundary conditions are one of the most common areas for beginners to make mistakes.

### 2.10.4 Grid and IBM Preview

The mesh and IBM preview pages are used to view the calculation area, mesh status, and identification of complex geometric surfaces.

The goal here is not for novices to analyze all mesh details, but to identify the most basic issues:

- Whether the grid can be recognized;
- Whether the geometry is in the expected position;
- Whether the fluid region and the solid region are obviously reversed;
- Whether the boundary selection is empty;
- Check whether the grid status reports an error.

If the preview appears empty, the range is clearly wrong, or the number of boundary selections is 0, it is not recommended to proceed with starting the formal calculation.

### 2.10.5 Operation monitoring

The run monitoring page is used to view whether COAST is running, as well as recent logs, step count, and output status.

You can use it to determine:

- Whether the program started successfully;
- Which step is currently reached in calculation;
-Whether Restart or Visit is written;
- Whether an error message appears;
- Whether the calculation needs to be stopped gracefully.

Note: A short step test should be done before official operation. Do not just leave a new study running for a long time.

### 2.10.6 Visit export and download

The Visit output page is used to organize the visualization results.

It usually helps you find:

- `Visit/solution.visit`;
- The corresponding `.vtk` chunked result file;
- Which time steps have been output;
- The set of files required to download or package the results.

Again: `solution.visit` is not the complete result itself. When sharing results, they need to be processed along with the `.vtk` file it references.

# 3. Modify calculation example settings

This chapter talks about "how to safely modify a COAST calculation example after it already exists." If you use the package version, it is recommended to copy `EXEC_TEMPLATE` first to get your own working example, such as `EXEC.demo`. All subsequent examples will use this name.

Note: Do not modify the template directory directly, nor treat running products such as `Restart`, `runtime_mesh`, `Decomp`, and `Visit` as configuration files to modify manually. The settings are mainly in several `*.d` files.

## 3.1 What can be changed in a calculation example?

A common working example looks roughly like this:
```text
EXEC.demo/
  input.d
  ibm_mesh.d
  boundary_conditions.d
  vtk_output.d
  spray.d
  spark.d
  probe.d
  heat_release.d
  mesh5_auto_refine.d
  Geometry/
  Fuels/
  Restart/
  Decomp/
  runtime_mesh/
  Visit/
```
The most suitable for ordinary users to modify here are the `*.d` files listed above. They are text configuration files read when COAST starts and runs, recording information such as "how to run this calculation", "where the grid and geometry come from", "what are the entrances and exits", "what results are output" and other information.

Generally do not change these directories manually:

- `Restart/`: Restart the data and save the last calculated flow field. If you delete it casually, the calculation may fail.
- `Decomp/`: Parallel chunking and compatible grid files. It is usually generated by mesh tools.
- `runtime_mesh/`: authoritative data of the runtime grid, related to restart and rank number.
- `Visit/`: Result output directory. This is suitable for viewing and archiving, not for changing settings.
- `Geometry/` and `Fuels/`: Geometry and fuel/mechanism data can be used as input, but novices should not replace them casually without understanding the units, coordinates and mechanism names.

## 3.2 What are `*.d` files?

`*.d` files are a type of text input file used by COAST. The `.d` here is not a programming language, nor is it a program that must be double-clicked to open; it is just an extension that represents a direct input file such as "direct input".

You can think of it as "calculation instructions". When COAST starts, it will read these files according to fixed rules:

- Some files are read line by line, and the position of the value is important. For example, many old-fashioned configurations in `input.d` have this style.
- Some files use a block structure, such as `&output_control ... /`, which is called a namelist, like a set of named options.
- `boundary_conditions.d` uses a patch structure that is closer to human readability to describe entrances, exits and walls.
- `#`, `!`, `C-----` Such lines are usually comments to explain the following content; comments are generally not treated as numerical values.

For example `input.d` might have a line like this:
```text
5000                             /lstep
500                              /stepsave : write restart file interval
500                              /stepplot : write plot file interval
```
means:

- `5000` is the total number of steps `lstep`;
- Write a restart every `500` steps;
- Write plot/Visit output every `500` steps.

Note: The old-fashioned file read by line cannot add or delete lines or change the order at will. You can change the value at the beginning of the line, but don't move the entire paragraph elsewhere.

## 3.3 Do two things before modifying

First, make sure you are changing the working example, not the template. The following command is executed in the package running directory, which is the directory where `bin/coastctl` and `EXEC_TEMPLATE` can be seen.
```bash
cp -a EXEC_TEMPLATE EXEC.demo
```
After execution, you should see an additional `EXEC.demo` directory. Subsequent modifications are made in `EXEC.demo`.

Second, make a backup copy of individual files before changing them. For example, if you want to change `input.d`:
```bash
cp -a EXEC.demo/input.d EXEC.demo/input.d.before_edit
```
There should be one more `EXEC.demo/input.d.before_edit` after execution. If you make corrections, you can restore specific lines against this backup.

Note: Do not use methods such as `git reset`, batch deletion, and clearing directories to "recover". There may be other people working on other files in the same workspace.

## 3.4 Graphical auxiliary interface What is the difference between modification and text modification?

The COAST package version provides a Chinese graphical auxiliary interface and also allows you to modify `*.d` files directly with a text editor. The two methods modify the same batch of calculation example files, but are suitable for different scenarios.

| How | What to do | Advantages | Risks |
| --- | --- | --- | --- |
| Graphical auxiliary interface modification | Novices can change common switches, view calculation case status, preview boundaries, check grids and outputs | It is not easy to find wrong files; the interface will display some files together; suitable for modification while viewing | The interface does not necessarily expose all advanced parameters; if multiple people modify the same calculation example at the same time, they may overwrite each other |
| Text modification | Accurately modify a certain line, copy the fragments given by others, and compare configurations in batches | Complete, direct, and reviewable; suitable for use when there is a clear modification goal | It is easy to miss semicolons, correct wrong units, and delete necessary lines, especially for old-fashioned sequential reading of files |

The recommended approach for newbies is:

1. Use the graphical auxiliary interface to review the general settings first to confirm which calculation example you are operating.
2. When you only need to change one or two items, you can change them in the graphical interface.
3. When you need to paste the complete boundary patch and accurately adjust the coordinate range, you can use a text editor to change it.
4. After changing the text, return to the graphical interface or use `coastctl` to check.

Note: Do not open the same file in the browser, graphical interface, and text editor at the same time and save it repeatedly. Save one side first, then refresh the other side.

## 3.5 Quick check on commonly used `*.d` files

| File | Main purpose | Frequently modified content for newbies | Special reminder |
| --- | --- | --- | --- |
| `input.d` | Global run control, restart, total steps, output interval, burning/PDF switch, time step and debugging switch | `lstep`, `stepsave`, `stepplot`, whether to restart, debugging output | Line order is very important; do not change the physical model you do not understand |
| `ibm_mesh.d` | Geometry/STL, IBM immersion boundary, mesh generation, mesh resolution, parallel tiling, Mesh-4 preview | Geometry file path, preview switch, target rank, mesh report | Changing it may cause mesh, restart and rank mismatch |
| `boundary_conditions.d` | Inlet, outlet, wall, coordinate selection, patch/STL selection, velocity temperature and pressure components | Inlet velocity, outlet pressure, wall temperature, methane/air component, coordinate range | Chapter 4 of this chapter explains in detail; must be previewed after modification |
| `vtk_output.d` | Which variables are output by Visit/VTK | Switch certain output fields and diagnostic levels | The more output, the larger the file size |
| `spray.d` | Spray, droplets, evaporation, nozzle position and spray output | Whether spray, spray fuel, nozzle parameters are enabled | Gas phase combustion studies usually remain off |
| `spark.d` | Ignition source, ignition time, ignition position, ignition duration | Ignition switch, ignition point coordinates, starting steps | Ignition position must fall in a reasonable fluid area |
| `probe.d` | Control of monitoring points such as pressure probes | Whether to enable, sampling interval | The current file may be very short, the common format is switch plus interval |
| `heat_release.d` | Global heat release rate history or diagnostic data | Usually not manually modified | May be written at runtime; only processed when it is clearly necessary to continue the heat release history |
| `mesh5_auto_refine.d` | Mesh-5 automatic local refinement candidate scoring | Whether to enable candidate generation and the weight of each score | Candidate generation is not equal to formal replacement of the solution mesh |

Explain one by one below.

## 3.6 `input.d`: running main switch

`input.d` is the most important global control file. It does not describe the specific entrances and exits, but tells COAST how the calculation example runs as a whole.

Common content includes:

- Whether to read old results from `Restart/` and continue calculation.
- Whether to write a new `Restart/` file.
- Total number of steps `lstep`.
- Write restart interval `stepsave`.
- Write interval `stepplot` for Visit/VTK results.
- Physical switches such as LES, combustion, reaction mechanism, PDF, compressible flow, etc.
- Time step limit, Mach number protection, debugging output and other running protection switches.

The most common modification for beginners is to make the total number of steps smaller and do a short test first. For example it turned out to be:
```text
5000                             /lstep
500                              /stepsave : write restart file interval
500                              /stepplot : write plot file interval
```
If you just want to run 50 steps first to see if it can start, you can change it to:
```text
50                               /lstep
25                               /stepsave : write restart file interval
25                               /stepplot : write plot file interval
```
This means running up to 50 steps, writing a restart and result every 25 steps. After passing the short test, increase the number of steps.

Regarding restarting, there is usually something like this in `input.d`:
```text
true true                   /restart, write to restart
```
The first `true` means reading from an existing restart, and the second `true` means continuing to write restarts while running. Beginners should note:

- If there are no files matching the current rank number in `Restart/`, but read restart is set, the operation will fail.
- If you're just starting from a clean template, you generally shouldn't force read restarts that don't exist.
- If you take a calculation example that has been run by others, make sure it can still be used after restarting before changing the rank number, grid or geometry.

The second half of `input.d` also has blocks like this:
```text
&time_control
  time_step_cap_enabled = .true.
  time_step_max = 9.9e-06
  time_step_growth_limit = 1.20
/
```
Each line in this block has a name, making it easier to read. The above indicates that the maximum time step limit is enabled. The maximum time step is `9.9e-06` seconds, and the new time step increases by up to 20% each time. If the calculation is unstable at the beginning, you can ask an experienced person to look at these protection parameters first. It is not recommended for novices to significantly relax themselves.

## 3.7 `ibm_mesh.d`: Geometry, Mesh, and IBM

`ibm_mesh.d` Pipe geometry and mesh. IBM is the abbreviation of immersed boundary method, which can be understood as the method of "using STL/CAD geometry to mark solids, fluids and walls in the background grid".

Common blocks in this file include:

- `&mesh_control`: whether to start mesh generation, whether to write preview, whether to overwrite the old `Decomp/`.
- `&mesh_runtime`: Which mesh the current solver uses as authoritative.
- `&mesh_regrid`: Mesh-4 preview and candidate mesh related settings. The current safe path is usually only labeling and previewing, and does not directly move the solution grid.
- `&ibm_control`: Whether to enable IBM, main geometry file path, STL units, wall damping, etc.
- `&mesh_geometry`: Geometry file list, STL/CAD units, geometry expansion or contraction.
- `&mesh_domain`: Computational domain range, which can be automatically derived from geometry or given manually.
- `&mesh_resolution`: basic grid spacing and minimum grid spacing.
- `&mesh_ibm`: fluid/solid markers, interface layers, CAD openings, etc.
- `&mesh_decomposition`: target MPI rank number, blocking method, forced alignment coordinate plane.

If you only change the inlet velocity, temperature, and outlet pressure in the existing calculation example, you generally do not need to touch `ibm_mesh.d`. If you replace the geometry file, change the mesh resolution, or change `target_ranks`, it may affect:

- Whether `Decomp/` needs to be rebuilt;
- Whether `Restart/` can still be used;
- Whether `runtime_mesh/` matches the current calculation example;
- Boundary coordinate selection whether the original entrance and exit can still be selected.

Note: `boundary_conditions.d` can only assign values ​​to existing boundary surfaces, and cannot "dig" solid areas in STL into entrances. If an internal nozzle does not have a fluid connection surface, you need to first create the opening through `ibm_mesh.d` and the mesh generation process, and then assign velocity and components in the boundary file.

## 3.8 `vtk_output.d`: Control Visit/VTK output

`vtk_output.d` determines which variables are written in the result file. The more Visit/VTK outputs, the easier post-processing is, but the file size is also larger.

Common writing methods are:
```text
default true
vtk_diag_level 1
01_Velocity true
02_Static_pressure true
02_Temperature true
04_Heat_release_rate true
```
It can be understood like this:

- `default true`: Fields not listed in the file are output according to the program's default behavior.
- `default false`: Only output fields explicitly written as `true`.
- `vtk_diag_level`: diagnostic level. The higher the level, the more diagnostic fields and the larger the file.
- `Field name true`: Output this field.
- `Field name false`: Turn off this field.

Newbies are advised to leave `default true` and a lower diagnostic level. Reduce the output only when the disk space is obviously insufficient, or when someone clearly tells you that only certain fields are needed.

## 3.9 `spray.d`: spray and droplets

`spray.d` controls spray, droplets, evaporation, mass/momentum coupling between droplets and gases, and nozzle geometry. Gas phase methane/air combustion studies typically maintain:
```text
spray = .false.
```
When `spray = .true.`, the `TCR_MULTI_INJECT` block later in the file defines the number of nozzles, droplet diameter distribution, spray position, direction, cone angle, particle rate and spray velocity.

Note: Spray is not as simple as "outputting a few more particle maps", it will change the computational physics process. Do not open when spray is not required.

## 3.10 `spark.d`: Spark settings

`spark.d` controls the ignition model, such as whether to ignite, ignition duration, ignition start time, maximum ignition temperature, number of ignition points and ignition coordinates.

Typical content might look like this:
```text
true      ! spark: true or false
0.005     ! spark duration time used by qdot_max (s)
0.0       ! spark initiation time used by legacy time model (s)
295.0 1800.0  ! initial air temperature and maximum spark temperature (K)
4         ! number of sparks
```
The following multiple lines of coordinates are the ignition point location, and the unit is usually meters. The ignition point should be located near a reasonable fluid area and flammable mixing area. If the ignition point falls inside a solid, outside a wall, or in an area with no fuel/oxidant at all, the calculation may run without ignition.

NOTE: There may also be a master switch for "ignition enabled" in `input.d`. Whether to actually ignite or not requires the content of the main switch and `spark.d` to be reasonable together.

## 3.11 `probe.d`: Probe settings

`probe.d` is used for simple monitoring settings such as pressure probes. In some current calculations, it may only have two short terms, for example:
```text
false  10
```
It can be roughly understood as settings such as "whether to enable" and "sampling interval". Ordinary users usually don't need to modify it if they just look at the overall field diagram and logs.

## 3.12 `heat_release.d`: Heat release rate history

`heat_release.d` usually saves historical data of global heat release rate changes over time. A common form is two columns of numbers: the first column is like time, and the second column is like heat release rate or related diagnostic quantities.

If an entry like the following in `input.d` is `false`:
```text
false                           /read global heat release rate: true/false
```
Then `heat_release.d` is more of a diagnostic result written at runtime. Only if you explicitly want to append from the existing global heat release rate history and set this read switch to `true` will it be used as an existing history.

Note: Do not treat `heat_release.d` as an ordinary parameter table and change it casually. Changing it will usually not help you "tune the combustion" but will make the historical diagnosis less credible.

## 3.13 `mesh5_auto_refine.d`: Automatic local refinement candidates

`mesh5_auto_refine.d` controls the scoring of Mesh-5 automatic partial refine candidates. It is not a switch to "immediately let the solver change the grid". Instead, it uses indicators such as geometry, vorticity, reaction rate, etc. to score areas that may need to be refined and generate candidate packages or reports.

Common content is similar to:
```text
enabled = false
on_restart = false
geometry_weight = 0.40
vorticity_weight = 0.30
reaction_weight = 0.30
top_fraction = 0.05
min_fluid_fraction = 0.02
```
means:

- `enabled = false`: Candidates are not automatically generated by default.
- `geometry_weight`: scoring weight close to the geometry/wall.
- `vorticity_weight`: vorticity related score weight.
- `reaction_weight`: reaction intensity related scoring weight.
- `top_fraction`: Select a part of the area with top scores.

NOTE: Candidate ciphers are suggestions only and not an official production grid. To actually use the new grid for calculations, you still need to go through the restarting and remapping, pre-checking and rollback protection processes. Beginners should not regard it as a button to "make the results more accurate with one click".

## 3.14 How to check after modification

Every time after modifying the `*.d` file, it is recommended to check it first before running it officially. The following command is executed in the package running directory, which is the directory where `bin/coastctl` can be seen.

The first step is to check whether the calculation example configuration can be read:
```bash
bin/coastctl case validate --case-dir EXEC.demo --json
```
You should see a JSON output. Under normal circumstances, there should be no obvious errors such as `error`, `failed`, and `missing`. This check mainly finds missing files, format errors, and obviously illegal configurations.

The second step is to check whether the boundary file can be parsed and previewed:
```bash
bin/coastctl boundary preview --case-dir EXEC.demo --json
```
This command only prints the preview and does not write additional files. You should see something like `COAST_BOUNDARY_PREVIEW_JSON`, `patchCount`, the name, type and selector of each patch.

If you want to save the preview results to the calculation example directory so that the graphical auxiliary interface or others can view them, you can run:
```bash
bin/coastctl boundary preview --case-dir EXEC.demo --write --json
```
After execution, `EXEC.demo/boundary_preview.json` is usually written out. Note: `--write` will modify your working example directory, so do not run `EXEC_TEMPLATE` directly.

The third step is to check the grid status:
```bash
bin/coastctl mesh status --case-dir EXEC.demo --json
```
You should pay attention to:

- Whether the number of ranks is consistent with the number of `mpirun -np` you plan to run;
- Whether the required mesh, tile or runtime mesh file can be found;
- If the geometry or mesh is changed, is it prompted that it needs to be regenerated or there is a mismatch?

If you are in the full development workspace instead of the packaged version directory, you can usually replace `bin/coastctl` with:
```bash
./coastctl case validate --case-dir EXEC --json
./coastctl boundary preview --case-dir EXEC --json
./coastctl mesh status --case-dir EXEC --json
```
## 3.15 Contents that are not recommended for novices to modify

The following are not absolutely impossible to change, but it is recommended that novices should not explore on their own:

- Chemical reaction mechanism name, such as `arm2`, fuel name, species list.
- Core physical models such as LES, PDF, micro-hybrid, and compressible models in `input.d`.
- Geometric units, fluid/solid notation conventions, mesh authoritative source in `ibm_mesh.d`.
- The number of ranks in `mesh_decomposition` and forced splitting, unless you know how to match the run rank and restart files.
- `targetMarker` in `boundary_conditions.d`, unless you explicitly know the numerical boundary path corresponding to the target marker.
- Spray coupling switch in `spray.d`, unless the study is a spray study.
- `Restart/`, `Decomp/`, `runtime_mesh/` internal files.

The current detailed chemical production default for the Methane/ARM2 study is still:
```text
chemistry_integrator dvode
chemistry_rhs_backend coast_legacy
chemistry_jacobian_backend internal_finite_difference
chemistry_dvode_mf 22
```
There is already a `generated_sparse_accumulated + mf=21` comparison backend in the program, but 2026-06-26
Hot benchmarks show no production performance benefit, so don't run it as the default setting.
To do development comparison, first read `SRC.Coast/docs/CHEMISTRY_PERFORMANCE_OPTIMIZATION_GUIDE.md`
and `EXEC/monitor/chemistry_stage1_benchmark.md`.

If you encounter any uncertainty, change one parameter first and do a short test and check. Do not change many items at once.

# 4. Boundary condition settings

Boundary conditions determine "where the fluid comes in, where it goes out, and what happens when it hits the wall." In COAST's clean EXEC workflow, it is recommended to only modify the entrance, exit and wall through `boundary_conditions.d`, and do not modify the Fortran source code or the old entrance profile file.

## 4.1 What are entrance, exit and wall?

You can first understand it in a daily life way:

- Inlet `inlet`: where the fluid enters the calculation area. You need to tell COAST the speed, temperature, pressure reference, gas composition, such as air inlet or methane inlet.
- Outlet `outlet`: The place where the fluid leaves the calculation area. You usually want to give an outlet pressure and indicate what temperature and composition to use as a reference if local backflow occurs.
- Wall `wall`: solid boundary. You need to indicate whether the wall velocity is zero, adiabatic, fixed temperature, and using a wall function.

A combustion chamber study usually has at least:

- one or more air inlets;
- one or more fuel inlets;
- an exit;
- External and internal geometric walls.

## 4.2 Basic structure of `boundary_conditions.d`

`boundary_conditions.d` consists of a set of `patches`. Each patch describes a type of boundary area, such as `main_air`, `methane_ring`, `outlet`, `external_adiabatic_walls`.

The minimum structure is as follows:
```text
version 1;

patch main_air
{
  kind inlet;
  type fixedVelocityInlet;
  enabled true;
  allowEmpty false;
  priority 10;

  selector
  {
    source externalBoundary;
    side west;
    marker any;
    region all;
  }

  targetMarker -1;
  U fixedValue (0 8.0 0);
  T fixedValue 295;
  p fixedValue 100000;

  composition volumeFraction
  {
    O2 0.21;
    N2 0.79;
    normalize true;
  }
}
```
Explained item by item:

- `version 1;`: Boundary file format version.
- `patch main_air`: Define a boundary block named `main_air`. The name must be unique.
- `kind inlet;`: This is the entrance. Can also be `outlet` or `wall`.
- `type fixedVelocityInlet;`: Entry type, here means directly given speed.
- `enabled true;`: Enable this patch. Setting to `false` is equivalent to temporarily disabling it.
- `allowEmpty false;`: Do not allow this patch to select even one side. Entrances and exits should usually be left `false`.
- `priority 10;`: priority. When multiple patches overlap, the one with higher priority is applied later and can overwrite the patch with lower priority.
- `selector { ... }`: Select which boundary faces belong to this patch.
- `targetMarker -1;`: COAST marker written after selection. It affects which boundary processing path the solver uses.
- `U`: speed, unit m/s.
- `T`: temperature, unit K.
- `p`: pressure, unit Pa.
- `composition`: gas composition.

NOTE: Most lines must have a semicolon `;` at the end. Missing semicolons and mismatched braces are the most common formatting errors.

## 4.3 `selector`: Which piece of boundary to choose?

`selector` is the most easily misspelled and most important part of the boundary file. It answers a question: To which mesh boundary surfaces should this patch be applied?

Common fields are as follows:

| Field | Function | Common writing methods |
| --- | --- | --- |
| `source` | Where to choose surface | `externalBoundary`, `ibmSurface` |
| `side` | On which side of the border or grid | `west`, `east`, `left`, `right`, `south`, `north`, `all` |
| `marker` / `markers` | What the original legacy marker must be | `marker -1;`, `markers (-5 -50);`, `marker any;` |
| `region` | Filter by geometric region on the selected side | `all`, `box`, `cylinderRing` |
| `patchGeometry` | Use additional patch STL files to assist identification | `patchGeometry 'Geometry/patches/air_inlet_ymin.stl';` |
| `patchTriangles` | Use recognized triangle patch numbers | Usually generated by graphical interface or sidecar |
| `cadFaceIds` | Use CAD/B-rep face numbers | Require reliable CAD face id |

`source externalBoundary` represents the external computational domain boundary, such as the entire entrance plane, exit plane, and shell boundary.

`source ibmSurface` represents a fluid-adjacent wall surface that already exists near the IBM geometry, such as a spout or wall identified on the STL internal geometry. It cannot create openings out of thin air.

The name of `side` comes from the grid generation and calculation example convention. Don't just guess based on the map orientation. Currently, the comments for some GTMC-type studies state that `side west` is the low `y` entrance and `side east` is the high `y` exit; another study may be different. The most reliable way is to look at the existing `boundary_conditions.d` comments, mesh preview and boundary preview.

`marker any` means "the original marker is not required to be a certain value". It's convenient, but also dangerous. This is only recommended when the coordinate range is very narrow and `source` and `side` are sufficiently clear. Otherwise, a patch may select faces that it should not select.

## 4.4 What is the difference between coordinate selection boundary and patch/STL boundary?

COAST supports two common boundary selection methods.

The first is patch/STL or CAD markup selection. It relies on additional geometry tags such as:
```text
patchGeometry 'Geometry/patches/air_inlet_ymin.stl';
```
This means "mark the air inlet area with this little STL file". If the geometry is well provided, this approach is intuitive and the graphical auxiliary interface can more easily display the corresponding areas.

Similarly, CAD/B-rep meshes can be used:
```text
cadFaceIds (43);
```
This means using CAD face numbering. This should only be written if `runtime_mesh/cad_faces.dat` or the geometry description explicitly tells you which physical boundary the face id corresponds to.

The second category is coordinate selection. It does not rely on patch STL, but uses boundary sides, coordinate range, and radius range to select. For example:
```text
selector
{
  source externalBoundary;
  side west;
  marker any;
  region cylinderRing;
  axis y;
  center (0 0);
  radiusRange (0.0 0.03);
  axialCoordinate y;
  axialRange (-1.0e30 1.0e30);
}
```
This means that on the `west` side outer boundary, select a circular area around the `y` axis with a radius from `0` to `0.03` meters.

The difference between the two can be recorded as follows:

| How | What to rely on | Advantages | Risks |
| --- | --- | --- | --- |
| patch/STL or CAD face | Reliable geometry tags, patch STL, CAD face id | Clear physical meaning, suitable for graphical interface click | If the label is missing, the path is wrong, or the face id changes, it will be empty |
| Coordinate selection | Coordinate axis, boundary side, radius or box range | No need to patch STL, suitable for STL calculation examples without labels | If the coordinate axis, unit, and range are written incorrectly, the wrong selection or empty selection will be made |

Note: patch STL is an "auxiliary tag" and is not a required condition. Without patch STL, coordinate selection is the officially supported notation.

## 4.5 How to set by coordinates when there is no patch STL

When the calculation example has only one overall STL and no separate entry/exit patch STL, you can write the boundary as follows.

The first step is to determine whether the boundary is an external boundary or an IBM surface:

- Domain outside entrance, domain outside exit, outside border wall: usually use `source externalBoundary`.
- STL internal geometric surfaces, spouts or walls near immersion boundaries: may use `source ibmSurface`.

The second step is to determine the `side`. If it is an external boundary, it must be as clear as possible which side it is. Don't use `side all` for entry/exit in the first place. `side all` is more suitable for wall patches like "all outer walls".

The third step is to select the geometric area.

Select the entire side:
```text
region all;
```
Select a rectangular range:
```text
region box;
bounds (-0.01 0.01 -0.02 0.02 -0.005 0.005);
```
The six numbers of `bounds` are:
```text
(xmin xmax ymin ymax zmin zmax)
```
Choose a circle, donut, or spout ring:
```text
region cylinderRing;
axis y;
center (0 0);
radiusRange (0.0069 0.0081);
axialCoordinate y;
axialRange (-0.00825 -0.00775);
```
Here `axis y` means that the axis of the ring is `y`, and the radius is calculated in the plane perpendicular to `y`. `center (0 0)` represents the coordinates of the center of the circle in this radial plane. For `axis y`, the radius is usually calculated from `x` and `z`.

The fourth step is to set `allowEmpty`.

Entry and exit recommendations:
```text
allowEmpty false;
```
In this way, if you cannot select any boundary faces, you will be reminded during the inspection phase instead of running silently.

Only certain optional wall patches are available:
```text
allowEmpty true;
```
Step five, preview. Coordinate selection without patch STL can also be previewed:
```bash
bin/coastctl boundary preview --case-dir EXEC.demo --write --json
```
You should see this in the output:

- `nonPatchStlCoordinateSelectorsSupported` is `true`;
- `name`, `kind`, `type` of each patch;
- Coordinate rules in `selector`;
- If you already have grid check data, you may also see `matchedFaces`, `empty`, `area`, `averageNormal`.

## 4.6 How to write speed, temperature, pressure and composition

### Speed `U`

The unit of velocity is m/s, and the three-dimensional vector is written as:
```text
U fixedValue (0 8.0 0);
```
The three numbers are `x`, `y`, `z` direction speed respectively. The above represents the velocity in the positive `y` direction, with magnitude 8 m/s.

If the flow direction is negative, write a negative number:
```text
U fixedValue (0 -8.0 0);
```
Note: The entrance velocity direction must be consistent with the calculation example coordinates. Don't just look at "left in, right out", make sure the actual axial direction is `x`, `y` or `z`.

Some IBM portals can use model velocity direction, for example:
```text
U model wallNormalIntoFluid;
U fixedValue (1 0 0);
```
In the fixed velocity entry, this type of writing means that the velocity direction is determined by the normal direction of the wall, `fixedValue`
Mainly provides speed size. In the mass flow entry, the velocity is automatically converted by `massFlowRate`,
`fixedValue` only needs to be a non-zero direction seed. Novices should not change the ordinary entrance to this model at will.
Unless the existing calculation example has been written in this way, or the developer explicitly requires it.

### Temperature `T`

The unit of temperature is K, which is Kelvin:
```text
T fixedValue 295;
```
`295 K` is approximately 22 degrees Celsius. Do not write the temperature in Celsius directly. For example, if you want to write 25 degrees Celsius, you should write about `298`, not `25`.

### Pressure `p`

The unit of pressure is Pa:
```text
p fixedValue 100000;
```
`100000 Pa` is approximately one standard atmosphere. The `p` in the inlet is often used as the reference pressure; the `p` in the outlet is usually more critical because it controls the pressure reference at the open boundary.

### Component `composition`

For ordinary users, it is recommended to use volume fraction:
```text
composition volumeFraction
{
  O2 0.21;
  N2 0.79;
  normalize true;
}
```
This represents an air volume fraction of 21% oxygen and 79% nitrogen. `normalize true` means allowing the program to normalize the proportions to avoid the sum not being 1 due to decimal errors.

For pure methane we can write:
```text
composition volumeFraction
{
  CH4 1.0;
  normalize true;
}
```
Quality score is also supported:
```text
composition massFraction
{
  CH4 0.055;
  O2  0.220;
  N2  0.725;
  normalize true;
}
```
Note: Species names are case-sensitive and must be consistent with the current chemical mechanism. Common effective gas phase species in the current methane/ARM2 calculation example are:
```text
CH4 O2 N2 CO2 CO H2O H2 OH O H
```
Cannot be written as `ch4`, `o2`, `Nitrogen`, `AIR`. If the species is not present in the mechanism, the run will fail during the check or startup phase.

## 4.7 Methane/Air Boundary Example

Below is a simplified methane/air example focusing on how to write it. Real studies should have their own coordinates, radii, sides and existing file comments.

Assumptions:

- The mainstream direction is positive `y`;
- Air enters from the low `y` outer boundary;
- Methane is injected from an IBM geometric ring;
- exit at high `y` outer boundary;
- Air temperature and methane temperature are both `295 K`;
- Reference pressure is `100000 Pa`.
```text
version 1;

patch main_air
{
  kind inlet;
  type fixedVelocityInlet;
  enabled true;
  allowEmpty false;
  priority 10;

  selector
  {
    source externalBoundary;
    side west;
    marker any;
    region cylinderRing;
    axis y;
    center (0 0);
    radiusRange (0.0 0.03);
    axialCoordinate y;
    axialRange (-1.0e30 1.0e30);
  }

  targetMarker -1;
  U fixedValue (0 8.0 0);
  T fixedValue 295;
  p fixedValue 100000;

  composition volumeFraction
  {
    O2 0.21;
    N2 0.79;
    normalize true;
  }
}

patch methane_ring
{
  kind inlet;
  type fixedVelocityInlet;
  enabled true;
  allowEmpty false;
  priority 20;

  selector
  {
    source ibmSurface;
    side all;
    marker any;
    region cylinderRing;
    axis y;
    center (0 0);
    radiusRange (0.0069 0.0081);
    axialCoordinate y;
    axialRange (-0.00825 -0.00775);
  }

  targetMarker -1;
  U model wallNormalIntoFluid;
  U fixedValue (40.0 0 0);
  T fixedValue 295;
  p fixedValue 100000;

  composition volumeFraction
  {
    CH4 1.0;
    normalize true;
  }
}

patch outlet
{
  kind outlet;
  type relaxedPressureOutlet;
  enabled true;
  allowEmpty false;
  priority 10;

  selector
  {
    source externalBoundary;
    side east;
    marker any;
    region all;
  }

  targetMarker -2;
  p fixedValue 100000;

  backflow
  {
    normalFraction 0.1;
    tangentialDamping 0.8;
    scalarBlend 0.1;
    T fixedValue 295;

    composition volumeFraction
    {
      O2 0.21;
      N2 0.79;
      normalize true;
    }
  }
}

patch external_adiabatic_walls
{
  kind wall;
  type noSlipAdiabaticWall;
  enabled true;
  priority 5;

  selector
  {
    source externalBoundary;
    side all;
    markers (-5 -50);
    region all;
  }

  targetMarker -5;
  U fixedValue (0 0 0);
  thermal adiabatic;
  species zeroGradient;
}
```
There are two entries in this example:

- `main_air` is the air inlet, priority `10`;
- `methane_ring` is the methane ring entrance, priority `20`, if it overlaps with a wider air region, it will be applied later.

Note: `side west/east`, radius and `y` range in the example are not universal constants. The scaling example must be adjusted based on geometry and preview.

## 4.8 Common entrance types

When the velocity is known, use `fixedVelocityInlet`:
```text
kind inlet;
type fixedVelocityInlet;
U fixedValue (0 8.0 0);
T fixedValue 295;
p fixedValue 100000;
```
When the total mass flow rate is known, `massFlowInlet` can be used:
```text
kind inlet;
type massFlowInlet;
massFlowRate fixedValue 0.06;
U fixedValue (0 1 0);
T fixedValue 295;
p fixedValue 100000;
```
Pressure-driven inlets can use `totalPressureInlet`:
```text
kind inlet;
type totalPressureInlet;
totalPressure fixedValue 101325;
U fixedValue (0 1 0);
T fixedValue 295;
```
Newcomers are given priority to use the entry types already used in existing calculations. If the original file uses `fixedVelocityInlet` and you just want to change the speed, don't change it to another type.

## 4.9 Common export types

A more reliable relaxation pressure outlet is commonly used in compressible combustion calculations:
```text
kind outlet;
type relaxedPressureOutlet;
targetMarker -2;
p fixedValue 100000;
```
If using a fixed static pressure outlet, you may see:
```text
kind outlet;
type pressureOutlet;
targetMarker -60;
p fixedValue 100000;
```
Exits also often come with a `backflow` block. What it means is: If a backflow occurs locally at the outlet, COAST needs to know the reference temperature and composition of the return air or gas. For example:
```text
backflow
{
  normalFraction 0.1;
  tangentialDamping 0.8;
  scalarBlend 0.1;
  T fixedValue 295;
  composition volumeFraction
  {
    O2 0.21;
    N2 0.79;
    normalize true;
  }
}
```
Novices generally only need to confirm that `p`, `T` and the return flow components are reasonable, and do not change the damping coefficient at will.

## 4.10 Common wall types

Adiabatic no-slip wall:
```text
kind wall;
type noSlipAdiabaticWall;
targetMarker -5;
U fixedValue (0 0 0);
thermal adiabatic;
species zeroGradient;
```
It can be understood that the solid wall does not move, the fluid velocity on the wall is 0, and the wall does not actively give or take away heat.

Fixed temperature no-slip wall:
```text
kind wall;
type noSlipIsothermalWall;
targetMarker -4;
U fixedValue (0 0 0);
thermal isothermal;
T fixedValue 500;
species zeroGradient;
```
It can be understood that the wall does not move and the wall temperature is fixed at `500 K`.

IBM wall function wall:
```text
kind wall;
type wallFunctionAdiabaticWall;
selector
{
  source ibmSurface;
  region all;
}
targetMarker -5;
U model wallFunction;
thermal adiabatic;
species zeroGradient;
wallFunction
{
  enabled true;
  dampingEnabled true;
  targetCfl 0.01;
  maxMultiplier 20;
}
```
This type of wall is usually prepared for near-wall processing with complex geometries and high Reynolds numbers. Newbies should not delete existing `ibm_wall_function` unless you know for sure that this study no longer uses IBM walls.

## 4.11 Boundary preview and graphical interface auxiliary files

After modifying `boundary_conditions.d`, run:
```bash
bin/coastctl boundary preview --case-dir EXEC.demo --json
```
If you just want to see the terminal output, use the above command.

If you want a GUI or other tool to read the preview file, run:
```bash
bin/coastctl boundary preview --case-dir EXEC.demo --write --json
```
After execution, something similar to this will be written in the calculation example directory:
```text
EXEC.demo/boundary_preview.json
```
Highlights from the preview:

- Is `patchCount` equal to the number of patches you expect;
- Whether the `name` of each patch is unique;
- Whether `kind` and `type` conform to the physical meaning;
- If `patchGeometryExists` is `false`, it means that the STL file pointed to by `patchGeometry` does not exist;
- If `empty` is `true`, it means that the patch is not selected;
- If `matchedFaces` is `0`, it usually means there is a problem with the selector coordinates, side, marker or geometry label;
- Whether `area` and `averageNormal` roughly match the entrance/exit area and direction expectations.

Graphical auxiliary interface Semi-automatic boundary processes may also use sidecars:
```bash
bin/coastctl boundary sidecar --case-dir EXEC.demo --write --json
```
This command will generate:
```text
EXEC.demo/boundary_patch_manifest.json
```
It is an intermediate format between graphical interfaces and border DSL. Usually the user does not need to write it by hand.

If you generate a boundary draft from a sidecar, you can run:
```bash
bin/coastctl boundary write-dsl --case-dir EXEC.demo --json
```
By default, it will be written as `boundary_conditions.generated.d` and will not directly overwrite the current `boundary_conditions.d`. Use `--apply` only when you explicitly want to replace it; when using `--apply`, the tool will back up the original file first.

Note: The automatically generated draft also requires manual inspection of speed, temperature, pressure, composition and coordinate range, and cannot be directly put into formal calculation after being generated.

## 4.12 Complete checking sequence after modifying the boundary

It is recommended to follow this order:

1. Save `boundary_conditions.d`.
2. Make a border preview.
3. Check the calculation example configuration.
4. Do a grid status check.
5. Do a test run of very short steps.

The first three commands are:
```bash
bin/coastctl boundary preview --case-dir EXEC.demo --write --json
bin/coastctl case validate --case-dir EXEC.demo --json
bin/coastctl mesh status --case-dir EXEC.demo --json
```
If an error occurs, do not run the solver yet. Prioritize fixing boundary files and mesh status.

For short tests, you can first change `lstep` in `input.d` to a smaller value, such as 20 to 50 steps. The short test can be started, the log has no obvious boundary errors, the Visit output can be turned on, and the official steps can be restored.

## 4.13 Common bugs and fixes

### Error 1: No patch can be selected.

Performance:

- `empty` is `true` in the preview;
- `matchedFaces` is `0`;
- The boundary is empty when the run is started.

Common reasons:

- `side` is written incorrectly;
- `source externalBoundary` and `source ibmSurface` are used reversely;
- The radius or coordinate range is too narrow;
- STL units are mm, but you understand the coordinates in a scale other than m;
- `marker` is too restrictive;
- `patchGeometry` path does not exist.

Correction method:

- Check the `patchGeometry` path first;
- Confirm which side the entrance/exit is based on the grid preview;
- Moderately relax the coordinate range;
- If you really don’t know the original marker, you can temporarily use `marker any` in a very narrow coordinate range;
- Do not directly change the entry `allowEmpty` to `true` to eliminate errors.

### Error 2: The entrance direction is written backwards

Performance:

- The speed near the entrance runs from inside the domain to the outside;
- The mass flow direction is wrong;
- The position of the flame or mixing zone is obviously abnormal.

Correction method:

- Confirm whether the mainstream direction is `x`, `y` or `z`;
- Use positive numbers in the positive direction and negative numbers in the negative direction;
- For IBM normal entrance, the `U model wallNormalIntoFluid` writing method in the original file is preferred.

### Mistake 3: Temperature unit is written in degrees Celsius

Wrong writing:
```text
T fixedValue 25;
```
Correct way to write:
```text
T fixedValue 298;
```
COAST uses K here. Writing the temperature too low will lead to unreasonable density, reaction and stability.

### Error 4: Wrong species name

Wrong writing:
```text
composition volumeFraction
{
  ch4 1.0;
  normalize true;
}
```
Correct way to write:
```text
composition volumeFraction
{
  CH4 1.0;
  normalize true;
}
```
Species names are case-sensitive. Currently, methane/ARM2 commonly uses `CH4`, `O2`, and `N2`, not `ch4`, `oxygen`, and `air`.

### Error 5: The sum of the components is unreasonable

If using:
```text
normalize false;
```
Then the sum of the components should be very close to 1. Newbies are advised to use:
```text
normalize true;
```
Writing `O2 21; N2 79;` can also be normalized for this type of ratio, but it is still recommended to write it directly as `0.21` and `0.79`, which is more clear.

### Error 6: The patch priority causes the coverage relationship to be reversed

For example, a large air inlet covers the entire inlet face, with small methane rings located within it. If the air patch had a higher priority, it might cover the methane ring.

Correction method:

- Use a lower priority for large-scale patches, such as `priority 10;`;
- Small-scale patches that need to be covered use a higher priority, such as `priority 20;`;
- The patch name must be unique.

### Mistake 7: Treating boundary files as hole-drilling tools

`boundary_conditions.d` can only select existing fluid boundary surfaces and assign values. It cannot turn a solid element into a fluid, nor can it open a new spout out of thin air on the STL wall.

If you need to add new internal entrances or exits, it is usually the mesh/IBM settings that need to be changed, such as geometry, opening faces, forced blocking planes, etc. This belongs to `ibm_mesh.d` and the mesh generation process, and cannot be solved by changing the boundary patch alone.

### Error 8: `targetMarker` can be changed at will

`targetMarker` looks like just a number, but it affects which boundary processing path COAST takes internally. Common conventions include:

- `-1`: common fixed entry path;
- `-2` or `-60`: common exit paths, which one to use depends on the calculation example;
- `-5`, `-50`: common adiabatic/zero gradient walls;
- `-4`, `-40`: common fixed temperature walls;
- `-3`: common slip or symmetry boundary.

When novices only change speed, temperature, pressure and components, do not change `targetMarker` casually.

## 4.14 Self-check list before and after boundary modification

Before submission or official operation, you can confirm item by item:

- Each `patch` name is unique.
- Each entry and exit has `allowEmpty false`.
- Each entry has `U`, `T`, `p`, `composition`.
- Outlet pressure `p` is reasonable, return flow `T` and composition are reasonable.
- The wall type matches `thermal`, for example `thermal adiabatic` is used for insulating walls.
- The unit of velocity is m/s, the unit of temperature is K, and the unit of pressure is Pa.
- Species names belong to current chemical mechanisms.
- The coordinate range unit is meters and is consistent with the calculation domain after STL unit conversion.
- The patch/STL path exists, or confirm that the patch is a pure coordinate selection.
- The `priority` of small-scale patches is higher than that of large-scale patches.
- There are no obvious errors in `coastctl boundary preview`, `case validate`, and `mesh status`.

After completing these checks, enter the "Operational Calculation" chapter for short tests and formal calculations.


# 5. Run the calculation

This chapter starts from "preparing to start calculation" to "how to see it when it is running". If you are using COAST for the first time, don't rush into long formal calculations. The recommended sequence is: do the pre-operation inspection first, then do the short test, and then do the formal calculation after passing the short test; if the formal calculation is interrupted or needs to be continued, follow the continued calculation process.

The following commands are executed in the portable package root directory by default, which is the directory where `bin/coastctl`, `bin/coast-ui`, and `EXEC_TEMPLATE` can be seen. Assume that your working example directory is called `EXEC.demo`.

Note: If you have installed the portable version using `install.sh` and have executed `source "$HOME/.local/coast/env/coast-env.sh"`, `bin/coastctl` in the command can be written as `coastctl`. If you haven't installed it yet and are just running it directly from the unzipped directory, continue using `bin/coastctl`.

## 5.1 Before starting the calculation, confirm which directory you are in.

A COAST calculation does not only run one file, but reads a "calculation directory". This directory usually contains:

- The main solver is provided by `bin/coast-solver` in the package directory; the calculation example directory mainly saves input, grid, restart data and output results;
- `input.d`: total control file, which contains whether to read Restart, total number of steps, output frequency, etc.;
- `boundary_conditions.d`: boundary conditions such as entrance, exit, wall, etc.;
- `ibm_mesh.d`: geometry, mesh, IBM related settings;
- `vtk_output.d`: Result output field settings;
- `runtime_mesh/`: runtime mesh;
- `Restart/`: Restart file for continued calculation;
- `Visit/`: post-processing result file;
- `screen`: Solver screen log; stdout/stderr and run manifest are placed outside the calculation in `.coast_run_logs/` by `coastctl`, and the specific path is viewed through `coastctl monitor`.

If you are starting from a template, you should copy `EXEC_TEMPLATE` first and do not calculate it directly in the template:
```bash
cp -a EXEC_TEMPLATE EXEC.demo
```
Execution location: root directory of the portable package.

After execution, you should see: There is an additional `EXEC.demo` folder in the current directory. In the future, modification, operation, and viewing results will all be based on `EXEC.demo`, and `EXEC_TEMPLATE` will remain as it is, making it easier to re-create clean calculation examples in the future.

Note: Do not put multiple different tasks in the same `EXEC.demo` and mix them for a long time. It is recommended to copy a new calculation example directory for each experiment and each working condition, such as `EXEC.case01`, `EXEC.case02`.

## 5.2 Pre-run checklist

The purpose of the pre-run check is not to "formally run a few commands", but to discover the most common problems in advance: the program does not exist, MPI cannot be started, the input file is written incorrectly, the boundary cannot be selected, the number of grids and restarts does not match, etc. Formal calculations are often time-consuming, and the sooner problems are discovered, the more time is saved.

It is recommended to check in the following order.

### 5.2.1 Check the running environment
```bash
bin/coastctl doctor --case-dir EXEC.demo --json
```
Execution location: root directory of the portable package.

This command will check:

- Whether the current directory is a COAST workspace or portable package;
- Whether the calculation example directory exists;
- Whether the main solver can be executed;
- Whether `mpirun` can be found;
- Whether `python3` can be found;
- Whether `boundary_conditions.d` exists;
- `runtime_mesh/` whether there is mesh information;
- Whether the number of `restart.NNN` in `Restart/` is reasonable;
- If `restart_pdf.NNN` exists, whether the number matches `restart.NNN`;
- Whether the rank numbers of `Decomp/`, `Restart/` and `runtime_mesh/` obviously conflict.

After execution you should see: a piece of JSON text. Novices don’t need to fully understand JSON, just focus on `"ok": true` or `"ok": true` in each check item. If an item is `false`, process this item first and do not continue to calculate.

Note: Passing `doctor` does not mean that the physical settings must be correct. It only confirms "whether it can start normally" and "whether there are any obvious gaps in the file structure".

### 5.2.2 Check input file format
```bash
bin/coastctl case validate --case-dir EXEC.demo --json
```
Execution location: root directory of the portable package.

This command will check whether the direct input file of the calculation can be recognized by the tool, especially suitable for running after you have modified the `*.d` file.

After execution, you should see: The JSON shows that the check was successful. If it fails, it is usually because a file is missing, the path is wrong, the field format is wrong, or there is a configuration issue clearly pointed out by the tool. Fix it first, then rerun the command.

### 5.2.3 Check whether the boundary condition can be selected
```bash
bin/coastctl boundary preview --case-dir EXEC.demo --write --json
```
Execution location: root directory of the portable package.

This command will read `boundary_conditions.d` and generate a boundary preview file, which usually reads:
```text
EXEC.demo/boundary_preview.json
```
After execution, you should see that each entrance, exit, and wall patch can be parsed. Focus on obvious empty selections, disabled items, spelling errors, or coordinate range errors.

Note: Boundary conditions can only "assign physical meaning" to existing boundaries and cannot harden the interior of a solid into a fluid inlet. If an entry cannot be selected, it is usually necessary to check the geometry, grid or coordinate range first, rather than just changing `kind` to something else.

### 5.2.4 Check grid status
```bash
bin/coastctl mesh status --case-dir EXEC.demo --json
```
Execution location: root directory of the portable package.

This command will summarize the runtime mesh of the current study, such as the mesh source, the number of mesh blocks, the geometry file, and whether there are any relationships between Restart and the mesh that need attention.

After execution, you should see: There is information such as `activeRuntimeMesh`, and the rank number and grid file are not empty. If you plan to continue the calculation, pay special attention to whether the current `runtime_mesh/` matches `Restart/runtime_mesh/`.

### 5.2.5 Schedule a run, but don’t actually start it yet
```bash
bin/coastctl run --case-dir EXEC.demo --ranks 128 --preflight --write --json
```
Execution location: root directory of the portable package.

The meaning of this command is: run according to the 128-rank plan and do pre-start checks, but do not actually start long-term calculations. It will write the plan and run-control status to the calculation external `.coast_run_logs/`. Do not leave a `.json` control file in the `EXEC.demo` root directory. The specific path can be viewed through the `stdoutLog`, `stderrLog` and manifest fields of `coastctl monitor`:
```text
.coast_run_logs/<case>/<run>/coast_run_plan.json
.coast_run_logs/_state/<case-key>.json
```
After execution, you should see: `"status": "planned"` in JSON, and the command will contain:
```text
mpirun -np 128 ../bin/coast-solver
```
Note: `128` here is just an example. How many ranks should be used in your calculation example depends on the number of blocks in `Decomp/`, `Restart/`, `runtime_mesh/`, and server resources. Don’t increase the rank arbitrarily just because the server has more cores.

If this preflight needs to prepare the old `Restart` to the new `runtime_mesh`, the C++ `coast_remap` backend will be used by default. The Python reference is only used when `--remap-backend python-reference` is explicitly added; there is no silent fallback when the C++ backend is not found.

## 5.3 What does rank mean?

`rank` is the number in MPI parallel computing, which can be simply understood as "distributing a large calculation to how many parallel workers". If 128 ranks are used, COAST typically starts 128 parallel processes, numbered 0 to 127. The common three-digit number in the file name is this number, for example:
```text
Restart/restart.000
Restart/restart.001
...
Restart/restart.127
```
`rank` is not a calculation of accuracy level, nor is the bigger the better. It is strongly related to the calculation case partitioning:

- `Decomp/grid_vv.*` represents old style chunking information;
- `runtime_mesh/block_*.dat` represents runtime mesh blocking;
- `Restart/restart.NNN` represents a continued calculation data saved by each rank;
- `Visit/solution.<step>.domain.<rank>.vtk` represents a block of results output by each rank.

The most important rules for beginners are:

- When running for the first time, use the prepared rank number of the template or calculation example;
- When continuing the calculation, try to use the same rank number as when writing Restart;
- As many ranks as there are in `Restart/restart.NNN`, the number of ranks is usually used when continuing the calculation;
- If there is `restart_pdf.NNN`, its number must be the same as `restart.NNN`;
- When in doubt, run `doctor` and `mesh status` first, and do not blindly change `--ranks`.

For example, there are a total of 128 files in `Restart/` from `restart.000` to `restart.127`, so when continuing the calculation, you should usually use:
```bash
bin/coastctl run --case-dir EXEC.demo --ranks 128 --preflight --write --json
```
If you change it to 64 or 256, the program may not be able to correctly read the existing Restart. At worst, it may fail to start, or at worst, it may read mismatched data.

## 5.4 What are Restart and PDF Restart?

`Restart` can be translated as "restart" or "continue file". It is not a result graph for people to see, but an archive for COAST to continue its calculations in the future. A long calculation may take a long time, and the state needs to be saved in the middle; you can continue from the saved state next time instead of restarting from the initial moment.

There are two types of common COAST restart files.

The first type is flow field Restart:
```text
EXEC.demo/Restart/restart.000
EXEC.demo/Restart/restart.001
...
```
It saves the main flow field data of each rank, such as velocity, pressure-related state, temperature-related state, etc. Newbies to the specific fields do not need to understand them one by one, as long as they know that it determines "where to continue the calculation."

The second category is PDF Restart:
```text
EXEC.demo/Restart/restart_pdf.000
EXEC.demo/Restart/restart_pdf.001
...
```
PDF Restart is related to PDF equations and combustion/mixing related random field states. It can be understood as "the continued calculation state of the combustion and mixing model itself". If the corresponding model is enabled for the calculation case, it usually needs to be saved and read when the calculation is officially continued.

There are usually several sets of important switches in `input.d`:
```text
true true                   /restart, write to restart
...
true true                   /read_pdf,write_pdf
```
The specific format of this type of line depends on your template, but the meaning is roughly:

- `read_restart`: Whether to read the existing `Restart/restart.NNN` during startup;
- `write_restart`: whether to write a new `Restart/restart.NNN` during operation;
- `read_pdf`: Whether to read the existing `Restart/restart_pdf.NNN` when starting;
- `write_pdf`: Whether to write a new `Restart/restart_pdf.NNN` during operation.

Common combinations are as follows.

| Scenario | `read_restart` | `write_restart` | `read_pdf` | `write_pdf` | Description |
| --- | --- | --- | --- | --- | --- |
| Start short test from initial conditions | `false` | `true` | `false` | Depends on the study | Do not read the old state, but can write the new one Restart |
| Continue calculation from existing flow field without PDF Restart | `true` | `true` | `false` | `true` | Common in the case of only cold flow field Restart |
| Resume from fully saved state | `true` | `true` | `true` | `true` | `restart.NNN` and `restart_pdf.NNN` are both complete |
| Only check startup, don't want to overwrite the results | Don't run it officially | Don't change it yet | Don't change it yet | Don't change it yet | Use `--preflight` first |

Note: If there is no `restart_pdf.NNN` in `Restart/`, do not set `read_pdf` to `true`. Otherwise the program will try to read a PDF Restart that does not exist, and will usually fail to start. You can first set it to `read_pdf=false, write_pdf=true` to let the program write a new PDF Restart in the new calculation; the calculation will be completely continued from these new files next time.

Note: Do not manually copy only part of `Restart/restart.NNN`. Missing the Restart of any rank may cause the calculation to fail.

## 5.5 Short test, formal calculation and continued calculation

The operation of COAST is recommended to be carried out in three steps: short test, formal calculation, and continued calculation. The difference between the three is mainly in the number of steps of `input.d`, the output frequency and whether to read Restart.

### 5.5.1 Short test

The goal of the short test is to confirm that "the calculation example can be started, can walk a few steps, can write logs, can write Visit, and can write Restart." Short measurements are not intended to draw final physical conclusions.

Before the short test, open `EXEC.demo/input.d` and change the number of steps and output frequency to be smaller. Notes may vary slightly from template to template, but common key items are:
```text
10                          /lstep
1                           /stepsave : write restart file interval
1                           /stepplot : write plot file interval
```
means:

- `lstep`: the maximum number of steps to be calculated;
- `stepsave`: write Restart every few steps;
- `stepplot`: Write Visit/VTK results every few steps.

The short test can be set to 10 steps, 20 steps or 50 steps. In order to quickly confirm the output link, `stepsave` and `stepplot` can be set to a smaller value first, such as 1, 5 or 10. The specific value should be combined with the scale of the calculation example. For calculation examples with large grids, it is not recommended to write a large number of results in each step.

Check first after modification:
```bash
bin/coastctl case validate --case-dir EXEC.demo --json
bin/coastctl boundary preview --case-dir EXEC.demo --write --json
bin/coastctl mesh status --case-dir EXEC.demo --json
bin/coastctl run --case-dir EXEC.demo --ranks 128 --preflight --write --json
```
After these are passed, start it:
```bash
bin/coastctl run --case-dir EXEC.demo --ranks 128 --execute --preflight --write --json
```
Execution location: root directory of the portable package.

After execution, you should see: The command quickly returns a piece of JSON, in which `"status": "started"`, and the running manifest and status file are written outside the calculation `.coast_run_logs/`:
```text
.coast_run_logs/<case>/<run>/coast_run.json
.coast_run_logs/_state/<case-key>.json
```
Note: This command starts background calculation. The return of the command does not mean that the calculation has been completed, it only means that COAST has started running. Follow up with monitoring commands to confirm the progress.

### 5.5.2 Formal calculation

After the short test is passed, `input.d` is changed to the number of steps and output frequency required for formal calculation. Formal calculations usually require attention to two things:

- Don't write the wrong order of magnitude in `lstep`;
- `stepsave` and `stepplot` should not be too small, otherwise the resulting files may be very large.

For example:
```text
5000                        /lstep
500                         /stepsave : write restart file interval
500                         /stepplot : write plot file interval
```
This is just an example and does not mean that all calculation cases should be set up this way. If novices do not have clear requirements, it is recommended to first ask the calculation example provider or project leader: how many steps to run, how often to save Restart, and how often to output Visit.

Still need to perform before formal calculation:
```bash
bin/coastctl doctor --case-dir EXEC.demo --json
bin/coastctl case validate --case-dir EXEC.demo --json
bin/coastctl mesh status --case-dir EXEC.demo --json
bin/coastctl run --case-dir EXEC.demo --ranks 128 --preflight --write --json
```
Start after confirming that everything is correct:
```bash
bin/coastctl run --case-dir EXEC.demo --ranks 128 --execute --preflight --write --json
```
Note: Do not edit `input.d`, `boundary_conditions.d`, `ibm_mesh.d`, `runtime_mesh/` or `Restart/` during formal calculation. These files are the input and state that the running program depends on, and changes during operation may lead to uninterpretable results.

### 5.5.3 Continue calculation

To continue the calculation is to continue the calculation from the existing `Restart/`. Before continuing the calculation, please confirm:

- The last calculation has been stopped normally, or at least a complete Restart has been written;
- The number of `Restart/restart.NNN` is consistent with the number of ranks;
- If you want to read PDF Restart, the number of `Restart/restart_pdf.NNN` is also the same;
- The current meshes corresponding to `runtime_mesh/` and Restart are not replaced arbitrarily;
- `read_restart` in `input.d` is turned on;
- `lstep` is set to the total number of steps or the number of subsequent steps you want to continue running, and is executed according to the current calculation example;
- Do `--preflight` first, then start.

Common checks before renewal:
```bash
bin/coastctl doctor --case-dir EXEC.demo --json
bin/coastctl mesh status --case-dir EXEC.demo --json
bin/coastctl run --case-dir EXEC.demo --ranks 128 --preflight --write --json
```
Start continuation calculation:
```bash
bin/coastctl run --case-dir EXEC.demo --ranks 128 --execute --preflight --write --json
```
After execution, view the `screen` or graphical auxiliary interface monitoring page. If it is a complete continuation, a prompt similar to "Restarting from previous solution" will usually appear in the log; if a PDF Restart is read, a prompt such as "Restarting Pdf Equation from Previous Solution" may also appear.

NOTE: Do not delete the old `Restart/` before continuation to "save space". If you must organize space, copy the entire study directory or archive `Restart/` and `Visit/` to a safe location before proceeding.

## 5.6 Using coastctl run

`coastctl run` is the recommended entry point for novices. It helps you generate a running plan, do pre-start checks, start background calculations, and record this running information.

### 5.6.1 Only generate plans
```bash
bin/coastctl run --case-dir EXEC.demo --ranks 128 --write --json
```
Execution location: root directory of the portable package.

Meaning: Generate a running plan, but do not check the input and do not start the program.

After execution you should see:
```text
.coast_run_logs/<case>/<run>/coast_run_plan.json
```
The plan will record:

- Calculation example directory;
- rank number;
- The command that will actually be run;
-Standard output log location;
-Standard error log location;
- Whether it is actually executed.

### 5.6.2 Do preflight check
```bash
bin/coastctl run --case-dir EXEC.demo --ranks 128 --preflight --write --json
```
Meaning: Automatically do `case validate` before starting, and then write the plan, but do not actually run it.

This is the most recommended step before official operation.

If Restart remapping is involved, this step checks and calls the C++ `coast_remap` production backend by default. Python reference is only used for explicit diagnostic commands:
```bash
bin/coastctl run --case-dir EXEC.demo --ranks 128 \
  --preflight --remap-backend python-reference --write --json
```
### 5.6.3 Really start the calculation
```bash
bin/coastctl run --case-dir EXEC.demo --ranks 128 --execute --preflight --write --json
```
Meaning: do preflight first, and then start it in the `EXEC.demo` directory:
```text
mpirun -np 128 ../bin/coast-solver
```
`stdout` will be written to the external running directory:
```text
.coast_run_logs/<case>/<run>/stdout.log
```
`stderr` will be written to the external running directory:
```text
.coast_run_logs/<case>/<run>/stderr.log
```
Running information will be written to the external running directory and external status index:
```text
.coast_run_logs/<case>/<run>/coast_run.json
.coast_run_logs/_state/<case-key>.json
```
Note: If there is already a running COAST, `coastctl run` will usually refuse to start again to avoid running two programs in the same calculation directory at the same time. Do not click "Start Run" repeatedly using multiple terminals.

### 5.6.4 If coastctl is not used, what is the underlying command?

Some developers or old scripts will run directly in the calculation example directory:
```bash
cd EXEC.demo
mkdir -p ../.coast_run_logs/manual
mpirun -np 128 ../bin/coast-solver \
  > ../.coast_run_logs/manual/EXEC.demo.stdout.log \
  2> ../.coast_run_logs/manual/EXEC.demo.stderr.log
```
This is an ordinary manual low-level startup method; the equivalent command in the source code version is `cd EXEC && mpirun -np N ./coast`. If MPI size differs from the active runtime mesh rank count, and `input.d` and Mesh-5 configuration allow startup regrid / restart remap, the startup phase will take the controlled preflight/write/remap path before solver reads fields. If preconditions fail, such as rank, file number, mesh identity, remap backend or gate conditions are not met, the shutdown should fail and the reason should be explained in the `screen` / JSON diagnostic.

It is more recommended for novices and production calculations to use `coastctl run`, because it will record the plan, check existing runs, unify the log location, and complete prepare/remap/activation through C++ `coast_remap` when needed.

Note: direct `mpirun` should not leave `.log`, `.json`, `.pid` or session temporary files in the `EXEC.demo` root directory. When it is necessary to temporarily redirect stdout/stderr, place it in `.coast_run_logs/`, a temporary directory or a user-specified archive directory outside the calculation.

Note: Do not run long studies directly without a limit on the number of steps. Before running, you must confirm that `lstep`, `stepsave`, and `stepplot` in `input.d` are the values ​​you want.

## 5.7 Optional auxiliary: monitor operation with graphical auxiliary interface

The graphical auxiliary interface is a graphical interface for novices. They can view the calculation status, edit input, start running, stop running, view Visit output and do basic post-processing in the browser.

### 5.7.1 Start the graphical auxiliary interface

On the Linux server, enter the root directory of the portable package and execute:
```bash
bin/coast-ui --workspace "$PWD" --case-dir "$PWD/EXEC.demo" --host 127.0.0.1 --port 18765
```
After execution, you should see: The graphical auxiliary interface service is running in the terminal and occupies `127.0.0.1:18765`.

If you use a browser on a Windows computer to access a remote Linux server, you need to do port forwarding in Windows PowerShell:
```powershell
ssh -N -L 18765:127.0.0.1:18765 user@server
```
Replace `user@server` with your server username and address. This PowerShell window should remain open. Then open it in Windows browser:
```text
http://127.0.0.1:18765
```
Note: `127.0.0.1` means "this machine". In the server command, it refers to the server itself; in Windows Explorer, it refers to Windows itself. The function of port forwarding is to connect Windows’ `127.0.0.1:18765` to the server’s `127.0.0.1:18765`.

### 5.7.2 How to view the operation in the graphical auxiliary interface

The operation monitoring of the graphical auxiliary interface usually calls:
```bash
bin/coastctl monitor --case-dir EXEC.demo --json
```
It will read:
```text
EXEC.demo/screen
.coast_run_logs/<case>/<run>/stdout.log
.coast_run_logs/<case>/<run>/stderr.log
```
There are several types of information you can pay attention to:

- Whether there is currently a `screen` file;
- The last recognized step or `istep`;
- Whether external `stdout.log` and `stderr.log` continue to grow;
- Whether error summaries such as `fatal`, `mpi error`, `abort`, `NaN`, `Inf` etc. appear;
- Whether there are new result files in `Visit/`;
- Whether there is a new continuation file in `Restart/`.

If you do not use a graphical auxiliary interface, you can also execute it in the server terminal:
```bash
bin/coastctl monitor --case-dir EXEC.demo --json
```
Or look at recent screen logs:
```bash
tail -80 EXEC.demo/screen
```
Execution location: root directory of the portable package.

Note: `tail -80` only looks at the last 80 lines and does not modify any files. It's great for quickly seeing where a program has gone.

## 5.8 Gentle Stop

Gentle stop means: do not kill the program directly, but tell COAST "Please stop at the appropriate location and try to write the file that should be written." This is safer than forcing a power off or directly killing the process.

Recommended commands:
```bash
bin/coastctl stop --case-dir EXEC.demo --json
```
Execution location: root directory of the portable package.

This command will create in the study directory:
```text
EXEC.demo/stop_coast
```
The COAST main program will check this file during operation. If it is found, it will try to stop at the appropriate time and write the corresponding output.

After execution, you should see: `createdStopFile` is shown as `true` in JSON, and the `stopFile` path is given.

Continue monitoring after stopping:
```bash
bin/coastctl monitor --case-dir EXEC.demo --json
tail -80 EXEC.demo/screen
```
If prompts similar to `stop_coast`, `time > tlast or istep > lstep: stop`, `finished`, or save Restart appear in the log, it means that the program is or has stopped according to the normal process.

Note: Gentle Stop does not mean "disappear immediately". Large calculation examples may not stop until the current step or current output is completed. Do not press Stop and Start continuously within a few seconds.

If there is no response after a gentle stop for a long time, and you confirm that it must be ended, you can use a forced stop:
```bash
bin/coastctl stop --case-dir EXEC.demo --force --json
```
Note: `--force` will attempt to send a termination signal to the running process, which is more risky than a gentle stop. After a forced stop, check whether `Restart/` is complete. You cannot default to the fact that the last result can be continued.

## 5.9 Which prompts indicate failure?

The following symptoms usually indicate a failure or at least a need to pause the check:

- `coastctl run` reports `mpirun not found`;
- `coastctl run` reports `missing executable`;
- `coastctl run` reports that it is already running and active;
- `errorSummary` of `coastctl monitor` is not empty;
- External `stderr.log` continues to grow, and `MPI error`, `abort`, `fatal` appear;
- `NaN`, `Inf`, `infinity` appears in `screen`;
- `Segmentation fault` appears in `screen`;
- The log prompts that the `restart` or `restart_pdf` file cannot be opened;
- The log indicates that the boundary configuration is incorrect;
- `Visit/` has no new files for a long time, and `screen` is no longer updated;
- The program exits quickly, but does not write the expected Visit or Restart;
- There is no prompt to read Restart when continuing calculation.

When encountering these situations, do not restart repeatedly. Gather information in Chapter 7's walkthrough order.

# 6. View and export results

The calculation results of COAST are mainly placed in the `Visit/` directory. Visit here refers to the VisIt post-processing software, not the English "visit". COAST will output index files and VTK data files that VisIt can read, helping you view slices, three-dimensional wholes, clouds, contours, and vector maps.

## 6.1 What are `Visit/solution.visit` and chunked VTK files?

When a calculation ends or is output, common result files are in:
```text
EXEC.demo/Visit/
```
The most important entry files are usually:
```text
EXEC.demo/Visit/solution.visit
```
It is not the complete data itself, but like a "directory listing". It lists which VTK files VisIt should read.

Really large amounts of data are usually found in files like these:
```text
EXEC.demo/Visit/solution.00000500.domain.000.vtk
EXEC.demo/Visit/solution.00000500.domain.001.vtk
...
EXEC.demo/Visit/solution.00000500.domain.127.vtk
```
It can be understood like this:

- `solution`: This is the solution result;
- `00000500`: usually represents the 500th step or a certain output step number;
- `domain.000`: 0th rank or 0th block;
- `.vtk`: a post-processing data format that VisIt can open.

If a calculation example is calculated with 128 ranks, then the same output step may correspond to 128 `.vtk` files. VisIt puts these chunks together into a whole through the `.visit` file.

## 6.2 Why `.visit` cannot be sent to others alone

The `.visit` file is usually small because it is just an index listing. It might just say:
```text
solution.00000500.domain.000.vtk
solution.00000500.domain.001.vtk
...
```
If you only send `solution.visit` to others without sending these `.vtk` files together, the other party will find that the data is missing when they open it. It's like sending someone the catalog of a book but not the text.

The correct way to share is:

- send `solution.visit`;
- Also sends all `solution.<step>.domain.<rank>.vtk` it references;
- Keep the relative path unchanged, preferably still in the same `Visit/` folder;
- If there are multiple output steps, make sure that the `.visit` and `.vtk` corresponding to each output step are complete;
- It is most recommended to use the Visit package download function of the graphical auxiliary interface, so that the system can automatically type the relevant files into a zip.

Note: Do not manually select just a few `.vtk` files to send, unless you know very well that you only want to see certain chunks. Both normal post-processing and archiving should preserve intact chunking.

## 6.3 Optional assistance: Download the Visit file using the graphical assistance interface

The graphical auxiliary interface will scan the `Visit/` directory and classify `.visit` and `.vtk` according to data groups. It will internally package the same set of results into a zip to prevent you from missing files.

The operation idea is as follows:

1. Start the graphical auxiliary interface;
2. Open `http://127.0.0.1:18765` in the browser;
3. Find results, Visit, post-processing or download related pages;
4. View the number of `.visit`, the number of `.vtk` and the total size of each set of data;
5. Select the required data group to download;
6. Download a compressed package similar to `coast_solution...zip`;
7. Keep the `Visit/` directory structure after decompression, and then use VisIt to open the `.visit` file inside.

The corresponding download logic of the graphical auxiliary interface will put the `.visit` and `.vtk` in the selected group into the zip together. If you select all results, the file may be very large, so you must first confirm that there is enough local disk space.

Note: If the graphical auxiliary interface displays `vtkCount` as 0, it means that it has not found the corresponding VTK data. There is no point in downloading `.visit` at this time. You should first check whether the calculation actually writes the result.

## 6.4 Download and install VisIt

VisIt is a commonly used scientific visualization software that can open `.visit` and `.vtk` files output by COAST. You can download it from the VisIt official website:
```text
https://visit-dav.github.io/visit-website/
```
Installation suggestions for newbies:

- Windows users download the Windows version installation package;
- Linux users can use the system package manager, the cluster installed version, or the official website download version;
- If the image is automatically generated through the graphical auxiliary interface on the server, the `visit` command also needs to be found on the server;
- If VisIt is not in the default path on the server, you can ask the administrator to set `COAST_VISIT_BIN` to point to the VisIt executable file.

Check if VisIt can be found on the server:
```bash
which visit
```
If there is output from this command, such as `/usr/local/bin/visit`, it means that the system can find VisIt. If there is no output, the automatic post-processing of the graphical assistant interface may prompt that VisIt cannot be found.

Note: VisIt is installed on the local computer to open the downloaded data by itself; VisIt is installed on the server to allow the graphical auxiliary interface to automatically generate images on the server. The two have different uses.

## 6.5 Open COAST results in VisIt

Take Windows local viewing as an example:

1. Download the Visit zip from the graphical auxiliary interface;
2. Unzip to a directory without Chinese special symbols and a path that is not too deep, such as `D:\coast_results\case01`;
3. Open VisIt;
4. Select `File` -> `Open file`;
5. Find `Visit/solution.visit` in the unzipped directory;
6. After opening, select the variables and drawing method to be displayed in VisIt;
7. Click on the `Draw` or similar button to draw.

If VisIt says it cannot find certain `.vtk` files, it is usually because:

- Only `.visit` was copied, not `.vtk`;
- The directory structure was changed during decompression;
- The file name was changed by network disk or chat software;
- Some `.vtk` are not downloaded completely;
- The `.visit` file refers to a relative path, but you separated it from `.vtk`.

Solution: Reuse the graphical auxiliary interface to package and download the complete group, and do not move individual files after decompression.

## 6.6 The meaning of common post-processing graphs

When novices open VisIt for the first time, they are most likely to be intimidated by the various plot types. It is enough to master the following ones first.

### 6.6.1 Pseudocolor: Pseudocolor cloud image

A pseudo-color image represents a scalar field in color. For example, areas with high temperatures are displayed in red, and areas with low temperatures are displayed in blue. It's suitable for viewing:

- Temperature distribution;
- pressure distribution;
- Density distribution;
- Component concentration;
- reaction progress;
- IBM or boundary markers.

Operation idea:

1. Add `Pseudocolor` picture;
2. Select a scalar field;
3. If the internal structure cannot be seen clearly, add `Slice` slice;
4. Click Draw.

### 6.6.2 Slice: slice

Slicing is to cut out a plane from the three-dimensional result. It is suitable for viewing internal flow fields because the three-dimensional whole may be obscured by external surfaces.

Common slicing directions:

- `slice_x`: slice perpendicular to the x direction;
- `slice_y`: slice perpendicular to the y direction;
- `slice_z`: Slice perpendicular to the z direction.

Graphical auxiliary interface These slicing modes are usually provided in automatic post-processing, and are cut at the 50% position by default, which is near the middle.

### 6.6.3 3D: three-dimensional whole

The three-dimensional whole is suitable for looking at geometric shapes, overall distribution and large-scale structures. However, if the variables mainly change internally, the three-dimensional whole may not be visible clearly, and slicing, transparency or isosurfaces are required.

### 6.6.4 Contour: Isoline or isosurface

Isolines/isosurfaces represent "where a certain variable is equal to some value." For example, an area where the temperature is equal to a certain value and an area where the component concentration reaches a certain threshold. It's suitable for viewing:

- Approximate position of the flame surface;
- Boundary of high temperature zone;
- The position where a certain component reaches a certain concentration;
- Layered structure of pressure or density.

### 6.6.5 Vector: vector image

Vector diagrams use arrows to represent direction and magnitude, most commonly velocity vectors. COAST's graphical auxiliary interface will combine a `COAST_velocity` vector field when it finds the three velocity components `01_Velocity_U`, `01_Velocity_V`, and `01_Velocity_W`.

Vector images are suitable for viewing:

- direction of flow;
- return flow area;
- Jet direction;
- The speed is generally strong or weak.

Note: The arrows will be unclear if they are too dense. You can increase the stride or reduce the number of arrows. Graphical auxiliary interface Automatic diagrams usually use a simplified arrow setup.

## 6.7 Optional auxiliary: use graphical auxiliary interface to generate basic post-processing images

If VisIt is installed on the server, the graphical auxiliary interface can automatically call VisIt to generate PNG images. It usually does these things:

- Scan the data group in `Visit/`;
- Find available scalar and vector fields;
- Select `Pseudocolor`, `Contour` or `Vector`;
- Select slice direction or 3D perspective;
- Call `visit -nowin -cli` to generate images in the background;
- Save the image to `Visit/postprocess/`.

The generated image is usually located at:
```text
EXEC.demo/Visit/postprocess/
```
If the graphical assistant interface prompts:
```text
VisIt executable not found; set COAST_VISIT_BIN or install visit
```
Explanation VisIt cannot be found on the server. The solution is to install VisIt, or ask your administrator to set it up:
```bash
export COAST_VISIT_BIN=/path/to/visit
```
Then restart the graphical assistant interface.

## 6.8 Saving images in VisIt

If you are viewing the results in the VisIt graphical interface, the general steps for saving an image are:

1. Adjust variables, slices, color range and viewing angle;
2. Select `File` -> `Set save options`;
3. Select the image format, such as PNG;
4. Set the resolution, such as 1280 x 900 or 1920 x 1080;
5. Select the save directory;
6. Click `Save window`.

When saving images, it is recommended that the file name contain:

- Calculation example name;
- Output the number of steps;
- variable name;
- Figure type;
- Slicing direction.

For example:
```text
case01_step05000_temperature_slice_y.png
case01_step05000_velocity_vector_slice_z.png
```
In this way, when you look back later, you can know the meaning of the picture without opening VisIt.

## 6.9 Results Archiving Recommendations

A complete and reviewable results archive should contain at least:

- `input.d` used this time;
- `boundary_conditions.d` used this time;
- `ibm_mesh.d` used this time;
- `vtk_output.d` used this time;
- `screen`;
- External `stdout.log`, `stderr.log` reported by `coastctl monitor`;
- The corresponding `coast_run.json` or `coast_run_plan.json` in `.coast_run_logs/`;
- `Visit/solution.visit` and corresponding `.vtk` that need to be reviewed;
- If the calculation needs to be continued later, complete `Restart/`;
- Pictures in `Visit/postprocess/` if GUI postprocessing is used.

Note: `Visit/` is for people to see the results, `Restart/` is for the program to continue calculations. The two have different uses and cannot be substituted for each other. Only `Visit/` cannot be continued, and only `Restart/` cannot directly view the complete regular results in VisIt.

# 7. Troubleshooting common problems

When you encounter a problem, don't panic or modify many files repeatedly. The most important thing for troubleshooting is to keep the scene: logs, input files, run plans, and result directories. Most of the clues to COAST common problems can be found in the external stdout/stderr logs reported by `screen`, `coastctl monitor`, `doctor` and `monitor`.

## 7.1 General troubleshooting sequence

It is recommended to collect information in the following order every time.

### 7.1.1 See doctor
```bash
bin/coastctl doctor --case-dir EXEC.demo --json
```
If there are already failed items here, they will be processed first. For example, `mpirun` does not exist, the main solver is not executable, and the number of `Restart` does not match, these are all problems that should be solved before starting.

### 7.1.2 View monitor
```bash
bin/coastctl monitor --case-dir EXEC.demo --json
```
Highlights:

- Whether `screenExists` is `true`;
- Whether `lastStep` has grown;
- Whether `stdoutBytes` and `stderrBytes` are abnormal;
- Whether `errorSummary` has content.

### 7.1.3 View recent logs
```bash
tail -120 EXEC.demo/screen
```
Execution location: root directory of the portable package.

The actual path to stdout/stderr is as reported by `bin/coastctl monitor --case-dir EXEC.demo --json`, usually under `.coast_run_logs/`. If a file does not exist, the program may not have written to it, or the startup phase failed. Absence itself is also a clue.

### 7.1.4 View key input files
```bash
sed -n '1,220p' EXEC.demo/input.d
sed -n '1,260p' EXEC.demo/boundary_conditions.d
```
Execution location: root directory of the portable package.

This step is not to let novices understand all the parameters, but to confirm whether there have been any obvious mistakes recently: whether the number of steps is outrageous, whether the Restart switch matches the file, whether the boundary coordinate range is written incorrectly, and whether the species name is misspelled.

### 7.1.5 Pause modifications and sort out problem descriptions

If you need to contact a developer or administrator, it is recommended to provide:

- Calculation example directory name;
- the order you execute;
- rank number;
- Which files have been modified recently;
- `doctor` output;
- `monitor` output;
- Last 120 lines of external `stderr.log` reported by `coastctl monitor`;
- Last 120 lines of external `stdout.log` reported by `coastctl monitor`;
- last 120 lines of `screen`;
- Whether it can be reproduced, that is, whether it fails again when running again.

Note: Don’t just say “It can’t be calculated anymore”. Without logs, it is difficult for others to determine whether it is an input problem, an MPI problem, a grid problem, a boundary problem, or a numerical divergence.

## 7.2 Graphical auxiliary interface cannot be connected

### Phenomenon

Browser opens:
```text
http://127.0.0.1:18765
```
But it shows that it cannot be accessed, the connection is refused, the page keeps spinning, or it cannot be opened.

### Common reasons

- `bin/coast-ui` is not started on the Linux server;
- The graphical auxiliary interface has exited after startup;
- port is not `18765`;
- SSH port forwarding for Windows PowerShell is not left open;
- The SSH login is not the same server;
- Server firewall or security policy blocks the connection;
- You confused the meaning of `127.0.0.1`;
- The browser accesses `http`, but it is copied to another address;
- The port is occupied by other programs.

### Processing steps

Restart the GUI on the Linux server:
```bash
bin/coast-ui --workspace "$PWD" --case-dir "$PWD/EXEC.demo" --host 127.0.0.1 --port 18765
```
Do not close this terminal. Then execute in Windows PowerShell:
```powershell
ssh -N -L 18765:127.0.0.1:18765 user@server
```
Don't close the PowerShell window either. Then the browser opens:
```text
http://127.0.0.1:18765
```
If it still cannot be opened, try another port, for example on the server:
```bash
bin/coast-ui --workspace "$PWD" --case-dir "$PWD/EXEC.demo" --host 127.0.0.1 --port 18766
```

Windows PowerShell：

```powershell
ssh -N -L 18766:127.0.0.1:18766 user@server
```
Browser:
```text
http://127.0.0.1:18766
```
Note: Do not use `--host 0.0.0.0` lightly. It causes the service to listen on more network addresses and is only suitable for trusted private networks or firewall-protected environments.

## 7.3 Port forwarding failed

### Phenomenon

Execute in PowerShell:
```powershell
ssh -N -L 18765:127.0.0.1:18765 user@server
```
An error is reported later, or the command seems to be running but the browser cannot be opened.

### Common reasons

- `user@server` is written incorrectly;
- SSH password, key or springboard settings are incorrect;
- Windows local `18765` port has been occupied;
- The GUI on the server is not running on `18765`;
- The server's SSH configuration disables port forwarding;
- Company or campus network restricts SSH;
- The PowerShell window is closed and the forwarding is disconnected.

### Processing steps

First confirm that ordinary SSH can log in:
```powershell
ssh user@server
```
If you cannot log in through ordinary SSH, first solve the account, network or key issues.

If normal SSH can log in, but port forwarding fails, change a local port:
```powershell
ssh -N -L 18766:127.0.0.1:18765 user@server
```
The meaning of this command is: Windows uses `18766` locally, and the server is still connected to `18765`. The browser should open:
```text
http://127.0.0.1:18766
```
If the server graphical auxiliary interface is also changed to `18766`, write `18766` on both sides:
```powershell
ssh -N -L 18766:127.0.0.1:18766 user@server
```
Note: `-N` means forwarding only and not opening the remote shell. It may not produce any output when running normally and appear to be "stuck", but it is actually maintaining the tunnel. Do not close this window.

## 7.4 `mpirun` is not started or cannot be found

### Phenomenon

`coastctl run` reports error:
```text
mpirun not found
```
Or the `mpirun` check in `doctor` failed.

### Reason

COAST relies on MPI for parallel operation. `mpirun` is a command to start multiple ranks. If the system cannot find `mpirun`, COAST cannot be started in parallel mode.

### Processing steps

Check on the server:
```bash
which mpirun
```
If there is no output, MPI cannot be found in the current environment. You can:

- Confirm whether the cluster module needs to be loaded first, such as `module load...` provided by the administrator;
- Confirm whether the environment script of the portable package needs to be executed first;
- Contact the administrator to install or configure MPI;
- Do not install multiple MPI versions and mix them at will.

If `which mpirun` has output but the operation still fails, first use monitor to find the external `stderr.log`:
```bash
bin/coastctl monitor --case-dir EXEC.demo --json
```
Common reasons include a mismatch between the MPI version and the program compilation environment, insufficient server resources, and the operating system does not allow running directly on the login node. In a cluster environment, it may be necessary to submit through the job scheduling system instead of `mpirun` directly.

## 7.5 Restart quantity and rank do not match

### Phenomenon

The calculation fails during continuation, or the `doctor` prompt is similar to:
```text
pdf=64 restart=128
decomp=64 restart=128
```
You may also see in the log that a certain `restart.NNN` or `restart_pdf.NNN` cannot be opened.

### Reason

Each rank requires its own Restart file. For example, if you use 128 ranks to continue the calculation, you usually need:
```text
Restart/restart.000
...
Restart/restart.127
```
If you also want to read PDF Restart, you also need:
```text
Restart/restart_pdf.000
...
Restart/restart_pdf.127
```
As long as one is missing, the numbers are not consecutive, and the quantities are inconsistent, the program may fail.

### Processing steps

First count the number of files:
```bash
find EXEC.demo/Restart -maxdepth 1 -name 'restart.[0-9][0-9][0-9]' | wc -l
find EXEC.demo/Restart -maxdepth 1 -name 'restart_pdf.[0-9][0-9][0-9]' | wc -l
```
Execution location: root directory of the portable package.

If `restart.NNN` is 128 and `restart_pdf.NNN` is 0, it means you may only have flow field Restart and no PDF Restart. Do not read PDF Restart at this time. Set `read_pdf` in `input.d` to false, but you can leave `write_pdf` as true and let the next section calculate and write a new PDF Restart.

If `restart.NNN` is 128 and `restart_pdf.NNN` is 64, don't force it. You need to retrieve the complete PDF Restart, or confirm whether you can regenerate it without reading the PDF Restart.

If the number of `restart.NNN` is inconsistent with your planned `--ranks`, do not randomly delete files to "make up the quantity". When you need to change the rank number or switch to a new runtime mesh, first use `coastctl run --preflight`; the production path defaults to writing staging through C++ `coast_remap`, and then controlled activation determines whether to replace active `Restart/runtime_mesh`.

Note: Changing from 128 rank to 64 rank does not mean simply deleting half of the files. That involves re-blocking or remapping, which is an advanced operation and requires developer confirmation.

## 7.6 Visit file is incomplete

### Phenomenon

VisIt reports an error after opening `.visit`, or only displays a part of the area, or a certain set of results in the graphical auxiliary interface shows that `.visit` is present but the number of `.vtk` is obviously wrong.

### Common reasons

- `Visit/` was copied before the calculation was finished;
- Only `.visit` was downloaded, not `.vtk`;
- The `.vtk` of some ranks is not written;
- Interruption during file copying;
- The disk is full, causing some results to be unfinished;
- You mixed `.visit` and `.vtk` from different calculation examples;
- The program exited abnormally during output.

### Processing steps

First look at the Visit group of the graphical auxiliary interface to confirm whether `vtkCount` is reasonable. The command line can also be roughly checked:
```bash
find EXEC.demo/Visit -maxdepth 1 -name '*.visit' | wc -l
find EXEC.demo/Visit -maxdepth 1 -name '*.vtk' | wc -l
```
If you know the rank number and the number of output steps, you can estimate the number of `.vtk`. For example, 128 rank, 1 output step, usually there are at least 128 corresponding `solution.<step>.domain.<rank>.vtk`.

Check the `.visit` reference content:
```bash
sed -n '1,80p' EXEC.demo/Visit/solution.visit
```
If the `.vtk` file listed there does not exist in the directory, the result is incomplete. Package and download from the graphical auxiliary interface again, or wait for the calculation to stop completely and confirm that the file is written before copying.

Note: Do not treat incomplete Visits as physical anomalies. It starts with a file integrity issue.

## 7.7 Boundary selection is empty

### Phenomenon

After running `boundary preview`, it is found that no boundary is selected for an entrance, exit or wall, or an error related to boundary configuration is reported soon after running.

### Common reasons

- The coordinate range in `boundary_conditions.d` is written incorrectly;
- `axis`, `side`, `bounds` and other selectors are inconsistent with the actual geometric direction;
- Misunderstanding of geometric units, such as mistaking millimeters for meters;
- The inlet position is inside the solid, not on the outer boundary of the fluid;
- `source ibmSurface` is used, but the corresponding IBM adjacent fluid surface does not exist;
- The patch name or STL tag does not exist;
- Boundaries were not rechecked after modifying the mesh.

### Processing steps

First generate a border preview:
```bash
bin/coastctl boundary preview --case-dir EXEC.demo --write --json
```
View the boundary file:
```bash
sed -n '1,260p' EXEC.demo/boundary_conditions.d
```
If you use coordinates to select boundaries, focus on checking:

- Whether the coordinate axis direction is correct;
- Are the minimum and maximum values reversed?
- Whether the numerical units are consistent with the geometry;
- Whether the selection range actually covers the boundary surface;
- Whether the internal area was selected by mistake.

If you're not sure about a geometric location, use the grid/IBM preview feature to check it first instead of guessing the coordinates.

Note: Do not directly expand to the entire domain when the boundary is empty. Wrong selection of the entrance, exit, and wall will make the calculation results meaningless. Even if the program can run, it does not mean it is correct.

## 7.8 Calculation failed or stopped early

Failure to calculate is not necessarily the same kind of problem. According to major categories, they can be divided into configuration problems, operating environment problems, grid/boundary problems, spray model problems, numerical divergence problems, etc.

### 7.8.1 Configuration issues

Common manifestations:

- Missing input file;
- A certain `*.d` format is wrong;
- The output frequency is 0 or unreasonable;
- Restart switch and file do not match;
- Misspelling of species name;
- The path points to a file that does not exist.

First run:
```bash
bin/coastctl case validate --case-dir EXEC.demo --json
bin/coastctl doctor --case-dir EXEC.demo --json
```
If they report an error, fix the configuration first.

### 7.8.2 Running environment issues

Common manifestations:

- `mpirun not found`;
-MPI error reporting;
- The program does not have permission to execute;
- The login node is not allowed to run for a long time;
- The disk is full;
- Insufficient memory;
- Repeated startup of the same calculation example directory.

examine:
```bash
which mpirun
ls -l bin/coast-solver
bin/coastctl monitor --case-dir EXEC.demo --json
```
If it is a cluster resource problem, you usually need to contact the administrator or use the job scheduling system.

### 7.8.3 Grid or IBM issues

Common manifestations:

- The log mentions IBM, mesh, STL, and mask;
- The border preview is empty;
- Abnormal grid status;
- The mesh saved in Restart is inconsistent with the current `runtime_mesh/`;
- Geometry changed, but still using old Restart.

examine:
```bash
bin/coastctl mesh status --case-dir EXEC.demo --json
bin/coastctl boundary preview --case-dir EXEC.demo --write --json
```
If you have changed the geometry or mesh, do not directly use the old Restart unless you have done Restart remapping and preflight according to a special process.

### 7.8.4 Numerical Divergence

Common manifestations:

- `NaN` appears in `screen` or external stdout/stderr log;
- `Inf` or `infinity` appears;
- Residual error, speed, temperature, and pressure suddenly become extremely large;
- Program abort in advance;
- A large area of unreasonable color appears in the result image, and then the program fails.

Numerical divergence may be caused by many reasons, such as too large a time step, unreasonable boundary conditions, too large a difference between the initial field and the boundary, poor mesh quality, incorrect physical property or component settings, too strong spray/combustion source terms, etc. Novices should not directly judge that "a certain model must be broken."

Collect first:
```bash
bin/coastctl monitor --case-dir EXEC.demo --json
tail -120 EXEC.demo/screen
```
The actual files for stdout/stderr are read from the `stdoutLog` and `stderrLog` fields in the `monitor` output.

Then record the step at which the failure occurred, which field was abnormal first, and which inputs were recently changed.

### 7.8.5 Normal early stop

Not all "stops" are failures. The following may be normal stops:

- reach `lstep`;
- The set end time is reached;
- User created `stop_coast`;
- The log appears `finished`;
- The log appears `time > tlast or istep > lstep: stop`;
- Write Restart and Visit before stopping.

This is a good thing if the program runs the short test and stops as expected. Don't think of "program exit" itself as an error.

## 7.9 `coastctl run` prompts that it is already running and is active

### Phenomenon

The startup times are similar to:
```text
existing coast run appears active
```
### Reason

`coastctl` records the last time in the external state file of `.coast_run_logs/_state/`
Started process number and check that this process still exists. It will prevent you from doing this in the same study directory
Repeated startup prevents two COASTs from writing the same batch of `Restart/` and `Visit/` at the same time.

### Processing steps

First monitor:
```bash
bin/coastctl monitor --case-dir EXEC.demo --json
```
If it is still running, do not start it again. If you need to stop, execute:
```bash
bin/coastctl stop --case-dir EXEC.demo --json
```
If you confirm that the previous process has ended but the record still exists, check the log and process status first.
Then contact someone with experience to handle it. Do not delete the status file in `.coast_run_logs/_state/`
Restart immediately unless you confirm that no old process is still writing files.

## 7.10 There are `fatal`, `abort`, `NaN` or `Inf` in the log

### Phenomenon

There is content in `errorSummary` of `coastctl monitor`, or the following appears in the log:
```text
fatal
abort
NaN
Inf
infinity
```
### Processing steps

The first step is to stop expanding losses. If the program is still running, stop it gently:
```bash
bin/coastctl stop --case-dir EXEC.demo --json
```
The second step is to save the scene. Do not delete `screen`, external stdout/stderr logs, `Restart/` or `Visit/`.

The third step is to collect logs:
```bash
bin/coastctl monitor --case-dir EXEC.demo --json
tail -120 EXEC.demo/screen
```
The actual files for stdout/stderr are read from the `stdoutLog` and `stderrLog` fields in the `monitor` output.

The fourth step is to recall recent changes:

- Whether the boundary conditions have been changed;
- Whether the inlet speed, temperature, pressure or composition has been changed;
- Whether the grid has been changed;
- Whether to continue calculation from the old Restart;
- Whether the rank number has been changed;
- Whether spray, ignition or combustion related settings are enabled;
- Whether the official step number and output interval were written incorrectly.

Note: Results generated after `NaN` or `Inf` should generally not be used as official results. Even if VisIt can be opened, it can only be used for troubleshooting and should not be used to report conclusions.

## 7.11 `Restart/runtime_mesh` is inconsistent with the current mesh

### Phenomenon

When resuming, the log or tool prompts that the mesh identity saved by Restart does not match the current `runtime_mesh/`, or mentions restart-to-new-mesh remap related information.

### Reason

Restart not only saves the digital field, but also is related to the current grid partition. COAST will now save the runtime mesh information corresponding to Restart to prevent you from hard-copying the old flow field to the new mesh.

If you change geometry, regenerate meshes, or change tiles, the old Restart may no longer be suitable for direct reading.

### Processing steps

First check:
```bash
bin/coastctl mesh status --case-dir EXEC.demo --json
```
If you just want to continue the last calculation, you should not replace `runtime_mesh/`. Retrieve the `runtime_mesh/` matched with Restart, or use the complete old calculation example directory to continue the calculation.

If you do move from an old mesh to a new mesh, this is part of the Restart remapping or Mesh-4/Mesh-5 advanced process. Novices should not move files manually to complete this operation. They should use `coastctl run --preflight` to view the controlled plan, and then use `coastctl run --execute` to complete the production prepare/remap/activation. Ordinary users can still use `cd EXEC && mpirun -np N ./coast` in the manual path; if MPI size differs and startup regrid / restart remap is allowed, the startup phase will take the controlled preflight/write/remap path before the solver reads fields. If it fails, it will fail to close and retain the diagnosis.

Common remap/preflight failure reasons include: missing `coast_remap`, inconsistent rank or number of files, failed marker transition gate, staging output directory already exists but overwrite is not allowed, or progress file is placed in output-dir.

## 7.12 The graphical auxiliary interface can be opened, but the startup fails.

### Phenomenon

The browser can open the graphical interface, but it fails after clicking Run.

### Common reasons

- The `--case-dir` pointed to by the graphical auxiliary interface is not the calculation example you want to run;
- The rank number is entered incorrectly;
- `case validate` failed;
- The server cannot find `mpirun`;
- The executable main solver cannot be found in the package directory;
- There is already a running COAST;
- The graphical auxiliary interface does not have permission to write the calculation example directory in the background;
- The Restart switch in `input.d` does not match the actual file.

### Processing steps

Return to the server terminal and execute the same command, and the error will be clearer:
```bash
bin/coastctl doctor --case-dir EXEC.demo --json
bin/coastctl run --case-dir EXEC.demo --ranks 128 --preflight --write --json
```
If you can't pass preflight, don't click official start in the graphical interface yet.

## 7.13 Graphical auxiliary interface post-processing failed

### Phenomenon

The graphical auxiliary interface can see the Visit data, but fails to generate images, prompting that VisIt cannot be found, or that a certain dataset, field, or plot type is not supported.

### Common reasons

- VisIt is not installed on the server;
- `visit` command is not in PATH;
- `COAST_VISIT_BIN` is not set or points to an error;
- `.visit` exists but the corresponding `.vtk` is incomplete;
- The selected field does not exist in the data set;
- Vector plot selected, but without full velocity components;
- VisIt background operation times out or reports an error.

### Processing steps

Check VisIt:
```bash
which visit
```
If there is no output, install VisIt or set up:
```bash
export COAST_VISIT_BIN=/path/to/visit
```
Then restart the graphical assistant interface.

Check Visit file integrity:
```bash
find EXEC.demo/Visit -maxdepth 1 -name '*.visit' | wc -l
find EXEC.demo/Visit -maxdepth 1 -name '*.vtk' | wc -l
```
If the field selection fails, first change to a scalar field that clearly exists in the graphical assistant interface as `Pseudocolor`, such as temperature, pressure or mark field. After confirming that the basic cloud chart can be generated, try the contour or vector chart again.

## 7.14 Insufficient disk space

### Phenomenon

The calculation fails during running, the Visit or Restart file is incomplete, the log may show that the file cannot be written, a file system error, or the server prompts quota exceeded.

### Reason

Both `Visit/` and `Restart/` can be large. When there are many ranks, high output frequency, and large number of steps, the number of files will increase rapidly.

### Processing steps

Check the study directory size:
```bash
du -sh EXEC.demo
du -sh EXEC.demo/Visit EXEC.demo/Restart
```
If there is insufficient space, stop the calculation first, and then confirm with the person in charge which old results can be archived or deleted. Do not delete files being written while the program is running.

Newbies can safely give priority to:

- Download and archive old Visit zips that are no longer needed for viewing online;
- Copy the complete calculation case and then clean the copy;
- Keep the most recent renewable complete `Restart/`.

Note: Don’t just keep `solution.visit` to save space. It cannot recover results alone.

## 7.15 When to stop and contact the developer

If the following situation occurs, it is recommended to stop trying and contact the developer or administrator after sorting the logs:

- Repeated occurrences of `NaN`, `Inf` or numerical divergence;
- The relationship between the number of restarts, the number of ranks, and the identity of the grid is unclear;
- After changing the grid, I want to continue calculation from the old Restart;
- `boundary preview` shows that the key entrance or exit is empty;
- `mpirun` or MPI reports a system-level error;
- There may be multiple processes writing files in the same calculation example directory at the same time;
- Both `Visit/` and `Restart/` are incomplete, but the results need to be restored;
- It is not sure whether Restart can still be used after forced stop;
- The log appears with `fatal` or `abort` that you cannot determine;
- Formal calculation results are used in reports, papers or engineering conclusions, but there are exceptions in the process.

When contacting please provide the information listed in Section 7.1. The more complete the information, the faster the positioning.

## 7.16 Troubleshooting Tips for Beginners

You can write down the order of investigation into one sentence:

Look at the environment first, then look at the input; do a short test first, then a long run; first warm up, then process; first package, then send; first keep the log, then ask for help.

Corresponding to the COAST file is:

- Environment: `doctor`;
- Input: `case validate`, `boundary preview`, `mesh status`;
- Run: `coastctl run --preflight`, `coastctl run --execute`;
- Monitoring: `monitor`, `screen`, external `.coast_run_logs/` stdout/stderr;
- Stop: `coastctl stop`;
- Result: `Visit/solution.visit` plus complete `.vtk`;
- Continuation calculation: full `Restart/restart.NNN`, and if necessary, full `restart_pdf.NNN`.

As long as you follow this order, most problems can be narrowed down to a clear scope instead of searching in a pile of documents.

## 8.2 Relationship between `SRC.Coast` and `EXEC`

`SRC.Coast` and `EXEC` are the most important pair of directories in the unpackaged version.

`SRC.Coast` is "where the program comes from". It contains COAST's Fortran/C++ source code, build files, test scripts, grid and restart tools, GUI backend, packaging tools, and AI agent skills.

`EXEC` is "where the program runs". It contains the current executable program `EXEC/coast`, the C++ Restart remapping backend `EXEC/coast_remap`, the current input files, geometry, fuel, running mesh, Restart data, Visit output and `screen`. The stdout/stderr, run manifest, and PID/session status of `coastctl` should be placed outside the calculation in `.coast_run_logs/` and should not pollute the `EXEC` root directory.

Common relationships can be written like this:

| Actions | Main Directory | Results |
| --- | --- | --- |
| Modify program source code | `SRC.Coast/` | Affects `EXEC/coast` after next build. |
| Builder | `SRC.Coast/` | Generate or update `../EXEC/coast` and `../EXEC/coast_remap`. |
| Change the calculation example parameters | `EXEC/*.d` | No need to recompile, but it must be verified before running. |
| Run calculations | `EXEC/` or `./coastctl run` | Read `EXEC` input, write `EXEC/screen`, `Visit/`, `Restart/`, etc.; run-control logs are written to external `.coast_run_logs/`. |
| Check mesh status | `./coastctl mesh status --case-dir EXEC` | Read `EXEC/runtime_mesh`, `EXEC/Decomp` and related identity files. |
| Make the portable package | Root directory `./coastctl package build` | Extract the running package from `SRC.Coast` and lightweight template, and output it to `dist/`. |

NOTE: Do not copy `SRC.Coast` into the portable runtime package. The portable package should only contain the binaries, template studies, graphical interfaces, documentation, and agent skills required to run it.

# 9. Description of Grid, Restart and Partial Encryption Methods

This chapter explains COAST's current grid and Restart methods. The average user does not need to understand each underlying algorithm, but does need to know which directories represent the current active state and which are just candidates or previews. Developers and AI agents need to strictly distinguish the responsibilities of Mesh-3, Mesh-4, and Mesh-5 to avoid mistaking candidate files for formal solution meshes.

## 9.1 First understand a few basic words

A grid divides a continuous calculation area into many small grids. COAST calculates physical quantities such as velocity, pressure, temperature, composition, PDF scalars, etc. on these grids.

Restart is restart data. It saves the calculation status of a certain step, and the calculation can be continued from this moment instead of starting from zero.

runtime mesh is the runtime mesh. The active mesh actually read by the current solver is:
```text
EXEC/runtime_mesh/
```
Decomp is a compatibility bridge still needed for old initialization code. In the current build/runtime grid mode, `EXEC/Decomp` should not be treated as manual authoritative input for arbitrary editing.

IBM is an immersed boundary method, which can be understood as "immersed boundary method" in Chinese. It uses markers to distinguish fluid regions from solid/wall regions, allowing complex geometries to be embedded in a structured background mesh.

The active solver mesh is the mesh that the current solver actually uses for calculations. Candidate meshes, preview meshes, and diagnostic meshes are not active solver meshes.

## 9.2 Mesh-3: Stabilizing the main line

Mesh-3 is the current stable solution main line, which can be understood as the "runtime consistent mesh" main line. In English, it is often written as `runtime_conformal` or runtime-conformal.

"Conformal" means that the mesh faces of adjacent blocks can be aligned. This is important to the solver because when adjacent MPI blocks exchange boundary data, they can swap paths with existing matching blocks without having to deal with non-matching surfaces of different thicknesses.

Key features of Mesh-3:

- Active mesh from `EXEC/runtime_mesh/`.
- `EXEC/Decomp/` still exists as a compatibility bridge, but is not a manual authoritative input for new grid work.
- There are matching interfaces between adjacent blocks and the existing `mpi_halo_exchange(field,hhalo)` fast path can still be used.
- Inlet, outlet, and wall boundaries are controlled by `EXEC/boundary_conditions.d`.
- STL geometry and coordinate/IBM selectors can work together and do not require that the current STL has a patch tag.

The current mesh authority in `EXEC/ibm_mesh.d` needs to be understood according to the mode:

| `mesh_source` | Meaning | Operation Notes |
| --- | --- | --- |
| `legacy_decomp` | The hand-prepared `EXEC/Decomp` is authoritative. | Only reasonable if `allow_run_from_decomp = .true.`. |
| `generated_decomp` | The integrated mesh generator writes out `Decomp` and uses it as the current source. | The build results still have to be checked by the tool. |
| `runtime_conformal` | `runtime_mesh` is the authority, `Decomp` is the compatibility bridge. | The current main line of thinking, do not manually modify `Decomp` when repairing. |
| `runtime_amr` | Reserved for true non-matching AMR. | Currently not production enabled, code should fail closed. |

NOTE: Mesh-3's stability comes from matched blocks and a controlled active mesh. Do not manually copy a candidate directory to `EXEC/runtime_mesh` for local refinement.

## 9.3 Mesh-4: New mesh Restart closed loop

The goal of Mesh-4 is not to dynamically refine at any time during the calculation process, but to allow COAST to safely complete this closed loop:
```text
Generate a new target mesh
  -> Preview and check
  -> Remap the old Restart to the new mesh
  -> Activate the new runtime_mesh
  -> Synchronize the Restart identity
  -> Validate with a short run
  -> Roll back if necessary
```
Mesh-4/Plan2 in the current workspace is already a closed-loop infrastructure. The current activity status record is:
```text
Active solver mesh: EXEC/runtime_mesh
Active mesh source: mesh4_axis_spacing_policy
Active grid: 109 x 319 x 106 over 128 ranks
Active Restart: EXEC/Restart remapped onto the promoted Mesh-4 target
Restart identity: Restart/mesh_identity.NNN must match runtime_mesh/mesh_identity.txt
```
Mesh-4 does several key things:

| Stage | Vernacular explanation | Key protection |
| --- | --- | --- |
| Target mesh generation | Prepare a new matching run mesh. | First as proposal/candidate, it does not directly cover the active grid. |
| Boundary/IBM Remark | Re-determine which cells are fluid, solid, inlet, outlet, and wall on the new grid. | Prevents loss of boundaries or IBM tags. |
| Restart remapping | Move the physical quantities on the old grid to the new grid. | Use fluid-solid mask, PDF protection, velocity/enthalpy protection. |
| activation preflight | Check the rank number, file number, and identity file before activation. | Reject startup if not matched. |
| promotion | Switch the target mesh to `EXEC/runtime_mesh`. | Requires synchronization Restart mesh identity. |
| rollback | Return to the previous active state when something goes wrong. | Preserve recoverable paths. |

If Mesh-4 promotion or rollback is done manually, the Restart identity must be synchronized:
```bash
cd /path/to/Coast_software
python3 SRC.Coast/tools/mesh4_activation_transaction.py \
  sync-restart-identity --exec-dir EXEC
```
Synchronizing identities means: Let each `mesh_identity.NNN` in `EXEC/Restart` match the activity `EXEC/runtime_mesh/mesh_identity.txt`. In this way, when restarting, the solver will not use the Restart of the old grid to configure the new grid.

Note: The Mesh-4 candidate preview file still has diagnostic value, but after activation the actual solution mesh only looks at `EXEC/runtime_mesh`.

## 9.4 Restart Vernacular explanation of interpolation and remapping

Restart remapping can be understood as "moving the weather values ​​on the old map to the grid on the new map."

The grid positions, sizes, and numbers of the old grid and the new grid may be different. You cannot simply copy `restart.000` to the new directory by file name, because the 100th grid may not be at the same spatial position on the old grid and the new grid.

Proper remapping requires doing the following:

1. Read the old Restart and old runtime mesh.
2. Read the target runtime mesh.
3. For each target fluid grid, find a reasonable old grid donor.
4. Perform interpolation or protective transfer of fields such as velocity, pressure, temperature, density, composition, PDF scalar, etc.
5. Check the old and new fluid-solid markers to prevent the fluid grid from borrowing values ​​from the solid donor.
6. Write the `restart.*`, `restart_pdf.*` and identity/manifest files corresponding to the new grid.

The production default tool is C++ `EXEC/coast_remap`. `coastctl run --preflight` and `coastctl run --execute` use this by default; Python reference is only used when `--remap-backend python-reference` is explicit.

`coast_remap` can also be used staging-only:
```bash
cd /path/to/Coast_software
EXEC/coast_remap \
  --restart-dir EXEC/Restart \
  --source-runtime-mesh EXEC/Restart/runtime_mesh \
  --target-runtime-mesh EXEC/Mesh5.target/runtime_mesh \
  --output-dir EXEC/Restart.remapped_mesh5_target \
  --overwrite-output \
  --allow-solid-to-fluid-nearest-donor \
  --progress-file /tmp/coast_remap_progress.log
```
It only writes `--output-dir` and does not override active `EXEC/Restart` or `EXEC/runtime_mesh`. `--rank-range A:B` or `--rank-list 0,4,7` can be used for diagnostic partial staging, but partial rank subset is not promotable and cannot be used in place of active Restart.

Common output includes:
```text
EXEC/Restart/restart.*
EXEC/Restart/restart_pdf.*
EXEC/Restart/restart.stat
EXEC/Restart/restart_payload_manifest.json
EXEC/Restart/restart_remap_manifest.json
EXEC/Restart/mesh_identity.NNN
EXEC/Restart/runtime_mesh/
```
Restart remapping check points:

| Check items | Why it matters |
| --- | --- |
| The number of `restart.*` is equal to the number of ranks | Each MPI rank requires its own Restart input. |
| The number of `restart_pdf.*` is equal to the number of ranks | When PDF Restart is turned on, each rank must have PDF status. |
| `Restart/runtime_mesh/` Consistent with the active mesh | The Restart run understands the geometry and IBM markup as per that snapshot. |
| `mesh_identity.NNN` matches `runtime_mesh/mesh_identity.txt` | Prevents the old mesh from being mixed into the new mesh during Restart. |
| manifest file exists | to facilitate tracking old meshes, new meshes and transfer methods later. |

You can use the following command to quickly count files:
```bash
cd /path/to/Coast_software
find EXEC/runtime_mesh -maxdepth 1 -name 'block_*.dat' | wc -l
find EXEC/Restart -maxdepth 1 -name 'restart.*' | wc -l
find EXEC/Restart -maxdepth 1 -name 'restart_pdf.*' | wc -l
```
If you plan to run with 128 ranks, the above three quantities should be compatible with your current run settings. If `read_pdf=true`, `restart_pdf.*` must also match.

Common reasons for remap failure include: missing `EXEC/coast_remap`, inconsistent number of source/target rank or Restart files, failed marker transition gate, `--output-dir` already exists without `--overwrite-output`, or `--progress-file` is placed within `--output-dir`.

## 9.5 Fluid-solid marking protection

Fluid-solid markers are the basis for COAST to distinguish between "here is a fluid" and "here is a solid/wall" in the IBM grid. The main conventions currently in the Visit preview are:
```text
IBM_marker = 1.0 means fluid
IBM_marker = 0.0 means solid
```
Core principles of fluid-solid mark protection:

- Fluid grids cannot borrow physics values from solid donors.
- Solid grids cannot be accidentally filled by normal fluid exchange.
- Fluid to solid and solid to fluid transitions are counted and reported.
- IBM wall adjacent inlet selection can only work on existing fluid adjacent surfaces.
- `boundary_conditions.d` can only select existing fluid boundaries, and cannot force solid grids into fluids.

For the average user, this means:

- If the portal preview is empty, do not blindly "brush out" the portal by expanding parameters.
- Entry may also be denied by the protection logic if there is only a thin fluid cap near the geometry.
- `source ibmSurface` selects the IBM wall surface adjacent to the fluid surface, rather than opening the solid wall.
- `source externalBoundary` selects the real outer boundary, not any MPI block surface.

For development/AI agents, the following checks are very important:
```bash
cd /path/to/Coast_software
python3 SRC.Coast/tests/check_boundary_source_semantics_static.py
python3 SRC.Coast/tests/check_ibm_surface_inlet_velocity_model_static.py
python3 SRC.Coast/tests/check_inlet_opening_depth_static.py
python3 SRC.Coast/tests/check_restart_marker_transition.py
```
These tests maintain several key behaviors: the outer boundary and the inner plane of the block cannot be confused, the direction of the entrance to the IBM surface cannot be chaotic, the entrance must have sufficient connectivity depth, and the Restart remapping cannot ignore fluid-structure conversion.

## 9.6 Mesh-5: Automatic local refinement candidates

The goal of Mesh-5 is to enable COAST to support true local refinement in the future, specifically where a parent patch is locally refined adjacent to a surrounding coarser mesh.

This thing is harder than Mesh-4 because adjacent blocks are no longer always face-to-face aligned. One side of the fine grid may correspond to the side of the coarse grid, with a different number of grids. This is called non-matching block exchange. The solver needs to know how to populate the thick and thin interfaces with ghost cells, protect velocity, pressure, temperature, composition, PDF scalars, and ultimately verify conserved fluxes.

Currently, Mesh-5 already has security scaffolding and candidate generation tools:
```text
SRC.Coast/tools/mesh5_single_block_refine.py
SRC.Coast/tools/mesh5_auto_refine.py
EXEC/mesh5_auto_refine.d
EXEC/Mesh5.auto_refined_candidate/
```
The automatic local refinement selector scores candidate parent blocks. Current rating sources include:

| Indicators | Vernacular explanation |
| --- | --- |
| Geometric Metrics | Areas with complex geometry, close to walls or changing boundaries may require finer meshes. |
| Vorticity Index | Locations where flow rotation or shear is strong may require finer meshes. |
| Reaction `dcdt` indicator | Locations where the combustion reaction changes rapidly may require a finer mesh. |

The default configuration file is:
```text
EXEC/mesh5_auto_refine.d
```
It is off by default. You can view or run candidate checks first:
```bash
cd /path/to/Coast_software
./coastctl mesh auto-refine --case-dir EXEC --json
```
To generate candidates all at once, you can use:
```bash
cd /path/to/Coast_software
./coastctl mesh auto-refine --case-dir EXEC \
  --enable-once --restart-auto-refine --json
```
You can also let the running plan generate candidates before Restart, but do not add `--execute` and look at the plan first:
```bash
cd /path/to/Coast_software
./coastctl run --case-dir EXEC --ranks 128 \
  --auto-refine-restart-candidate --auto-refine-force \
  --preflight --write --json
```
Note: automatic local refinement currently generates candidates, that is, candidate packages. The candidate package is not an active solution mesh.

## 9.7 Why Mesh-5 candidates cannot be used directly as active solver mesh

This is one of the most important safety rules in this chapter:
```text
Mesh-5 candidate != active solver mesh
```
You cannot directly copy `EXEC/Mesh5.auto_refined_candidate` to `EXEC/runtime_mesh` for the following reasons:

| Reason | Explanation |
| --- | --- |
| Non-matching exchange is still in the verification stage | Thick and thin interfaces require a special halo schedule, and not all production scenarios have been verified. |
| Candidates may change the number of blocks and rank mapping | A parent block may be split into 8 child blocks, and the number of Restart files will also change accordingly. |
| The candidate is written with activation access control | The current candidate will be marked with a status similar to `safe_for_restart_remap_target false`, indicating that it cannot be directly promoted to the production grid. |
| Restart has not completed remapping the new target | There is no corresponding new mesh Restart, the solver cannot safely continue. |
| Fluid-solid markers and boundaries need to be revalidated | IBM markers, entry depth, and boundary selection may all change after local refinement. |
|Conservative fluxes still need to be verified |The mass, momentum, enthalpy, and component fluxes of the thick and thin interfaces must eventually be subject to conservation checks. |
| The lack of rollback protection can be dangerous | There is no way to reliably return to the last active Mesh-4 state when something goes wrong. |

Candidate packages can do the following:

- Show developers where local refinement is appropriate.
- Generate non-matching interface materials such as `interfaces.dat`, `interface_<rank>.dat` and so on.
- Record parent/child lineage, thickness ratio, marker transition diagnostics.
- Use test scripts to verify C++ runtime schedule, pack/unpack, coarse-to-fine interpolation, and fine-to-coarse averaging.

Candidate packages cannot do these things:

- Cannot directly replace `EXEC/runtime_mesh`.
- You cannot directly configure the old `EXEC/Restart` to start production solving.
- Cannot bypass Mesh-4 remap, activation preflight and rollback.
- Cannot be used as evidence of "Completed Dynamic AMR".

## 9.8 Mesh-5 follow-up goals

The long-term goal of Mesh-5 is to build a static, precomputed non-matching block switching layer. It does not do dynamic AMR first, but first allows a local refinement target to run safely.

Target capabilities include:

- A parent block can be refined in one or more directions.
- When coarse blocks and thin blocks are adjacent, run the grid record thickness interface.
- ghost cell exchange supports scalar, PDF scalar, density, temperature, pressure and velocity.
- Interface diagnostics can report maximum jump, average jump, and conservation drift.
- A refinement parent block can be split into multiple child blocks, for example 8 child blocks of `2 x 2 x 2`.
- Load balancing is estimated by active fluid unit workload, not just by background grid count.
- Mesh-4's Restart remap and activation transaction are still responsible for new mesh promotion.

Current relevant tests include:
```bash
cd /path/to/Coast_software
python3 SRC.Coast/tests/check_mesh5_runtime_schedule_active.py
python3 SRC.Coast/tests/check_mesh5_candidate_active_segments.py
python3 SRC.Coast/tests/check_mesh5_mpi_active_exchange.py
python3 SRC.Coast/tests/check_mesh5_single_block_refine.py
python3 SRC.Coast/tests/check_mesh5_synthetic_exchange.py
```
Only when the current case of the matching block is not affected, thick and thin interface exchanges pass, Restart can enter short time stepping, Visit can see the interface diagnosis clearly, and rollback is still available, can Mesh-5 gradually approach production use.

## 10.5 Security Cleanup Rules

Before cleaning, make sure no calculations are running:
```bash
pgrep -af 'mpirun|mpiexec|./coast|EXEC/coast' || true
```
If you see that there are still `mpirun` or `coast` processes, do not clean them yet. When you need to stop, use:
```bash
cd /path/to/Coast_software
./coastctl stop --case-dir EXEC --json
```
Cleaning rules are divided into three categories.

### Content that can be cleaned up after confirmation

These are usually external temporary logs, old candidates or old release packages, but it is still recommended to take a look at them:
```bash
cd /path/to/Coast_software
ls -ld .coast_run_logs 2>/dev/null || true
find EXEC -maxdepth 1 \( -name '*.log' -o -name '*.json' -o -name '*.pid' \) -print
ls -ld EXEC/Mesh5.auto_refined_candidate 2>/dev/null || true
ls -ld dist/* 2>/dev/null || true
```
After confirming that it is not needed, you can archive the external `.coast_run_logs/` or the `.log/.json/.pid` mistakenly placed in the `EXEC` root directory to a user-specified location. Do not delete real files by default in the documentation process; old package directories, old candidate directories, and old isolated run directories can only be deleted after confirming that they are no longer used for reproduction, auditing, or comparison.

### Don’t clean up the content casually

The following directories and files should not be deleted without explicit authorization:
```text
EXEC/Restart/
EXEC/runtime_mesh/
EXEC/Decomp/
EXEC/Geometry/
EXEC/Fuels/
EXEC/*.d
EXEC/coast
EXEC/coast_remap
SRC.Coast/
docs/
```
Special attention:

- `EXEC/Restart/` may be the only entry for continuation.
- `EXEC/runtime_mesh/` is the currently active solver mesh.
- `EXEC/Decomp/` is still a compatibility bridge and cannot be deleted just because it "looks old".
- `EXEC/Geometry/` and `EXEC/Fuels/` are geometry and chemistry inputs.
- `EXEC/*.d` is a direct input file, not a temporary file.
- `EXEC/coast` and `EXEC/coast_remap` are the solver and C++ remap production backends respectively.

### Cleaning of Visit output

`EXEC/Visit/solution.visit` itself is just an index file, which references many `solution.<step>.domain.<rank>.vtk` files. Deleting just `.visit` or just deleting VTK will make the result incomplete.

Estimate the size before cleaning Visit:
```bash
cd /path/to/Coast_software
du -sh EXEC/Visit
find EXEC/Visit -maxdepth 1 -type f | wc -l
```
It can only be cleared if the user confirms that the results have been archived or are no longer needed. It is best to create an archive or clearly record the reason for deletion before cleaning.

### Organize into a clean workspace before transplantation

If the goal is to move the unpackaged workspace to another machine, it is recommended to retain these directories and files:

where `EXEC/` should only retain the current program and reusable study assets, for example:

## 10.6 Failure troubleshooting sequence

When the operation fails or the result is abnormal, it is recommended to read in the following order:

1. `./coastctl monitor --case-dir EXEC --json`, especially `stdoutLog`, `stderrLog` and `errorSummary`.
2. stdout/stderr and run manifest pointed to by monitor in external `.coast_run_logs/`.
3. `EXEC/screen`, this is the main screen log.
4. `EXEC/input.d`, `EXEC/boundary_conditions.d`, `EXEC/vtk_output.d`, `EXEC/spray.d`, `EXEC/spark.d`, `EXEC/probe.d`, `EXEC/heat_release.d`.
5. `EXEC/ibm_mesh.d` and the current `EXEC/runtime_mesh/` state.
6. `SRC.Coast/` source code.

Look at the end of the log:
```bash
cd /path/to/Coast_software
./coastctl monitor --case-dir EXEC --json
tail -120 EXEC/screen
```
The actual files for stdout/stderr are read from the `stdoutLog` and `stderrLog` fields in the `monitor` output.

Before changing the source code of the development/AI agent, the failure phenomenon, last log, input settings and current mesh/Restart status should be recorded. Many failures come from input, rank number, Restart file number, empty boundary selection, or mesh identity mismatch, and do not necessarily require changes to the solver source code.

## 10.7 The last few red lines

These rules bear repeating:

- Do not restore old `boffin`, `config_boffin`, `coast-solver`, `coast-solver-TCR` names to active source, script or executable paths.
- Do not treat the Mesh-4 candidate preview file as the active solution mesh.
- Do not copy Mesh-5 auto-refinement candidates directly into `EXEC/runtime_mesh`.
- Do not enable `mesh_regrid.mode='dynamic'` or `mode='conservative_transfer'` for production runs.
- Do not use `boundary_conditions.d` to force a solid grid into a fluid.
- Do not initiate a Restart run without confirming that the rank, Restart, PDF Restart, and runtime mesh file numbers match.
- Do not remove `EXEC/Restart`, `EXEC/runtime_mesh`, `EXEC/Decomp` or `EXEC/screen` while running.
- Do not package the running directory manually, you must use `coastctl package build`.

By adhering to these red lines, the unpackaged version of the workspace can simultaneously serve normal operation, development verification, AI agent collaboration, and portable release.
